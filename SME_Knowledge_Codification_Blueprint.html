Latest grounded assessment

OntoWiz is a working governed-pack foundation, not yet an end-to-end context factory.

The system already has credible artifact, Delta, compiler, registry, REST/MCP, catalog, evaluation and Forge kernels. The architecture has now converged on a domain-independent Context Platform with separate control, build and data planes. The missing center is the production pipeline from raw client evidence and SME dialogue to verified, released and agent-ready context.

How to read this blueprint

Verified means the authoritative audit gate passed. Submitted means code exists on an isolated review SHA but INT has not accepted it. Specifications and prototypes are not counted as shipped capability.

03

Accepted architecture

The platform remains one modular monorepo, but knowledge truth and client evidence live outside the platform repository.

KP_SDLC Delivery governance, task isolation, mini-specs, gates, evidence bundles and reviewer independence. Never: a knowledge store.
→
OntoWiz Platform Contracts, curation, Deltas, compiler, validation, evaluation, release, typed serving and operations. Never: the permanent home for confidential client source content.
→
Domain Pack Repositories Shared base packs and private client overlays pinned to immutable source commits and evaluated releases. Never: a fork of the platform compiler or schema.
Control plane Govern and operate

Catalog, source library, curation, approvals, evaluation metadata, releases and administration. Tier A serve plus governance adapter.

Build plane Compile and evaluate

Isolated Tier B workers with controlled source access and model credentials. They may propose and build, but cannot activate directly.

Data plane Serve agents

Per-tenant, key-free runtime for verified releases, projections, context resolution, retrieval and agent traffic.

System of record

Raw evidence

Client DMS, Veeva, SharePoint, warehouse or controlled object store. Raw documents do not enter Git.

Approved semantic truth

Domain pack source

Immutable client-pack commit produced through approved Delta materialization.

Released truth

Candidate + receipts + attestation

Immutable compiled candidate bound to passing receipts and a release decision.

End-to-end context factory

The architecture is generic across marketing, sales, market access, patient services, supply chain and launch. Status markers show the current implementation reality.

1. Missing

Register sources

Identity, content hash, rights, access class, tenant, applicability and immutable source versions.

2. Specified

Parse safely

Model-free PDF, DOCX, TXT and VTT into normalized units, chunks and reconstructable spans.

3. Missing

Extract candidates

Bounded typed stages propose entities, terms, questions, decisions, metrics, rules and playbooks.

4. Missing

Reconcile

Exact identity, governed aliases, disagreement, contradiction, coverage and evidence sufficiency.

5. Partial verified

Govern

Deltas, approvals, audit and lifecycle exist; source-candidate integration and hardening remain.

6. Submitted

Compile candidate

Deterministic exact inventory and fresh atomic writes are on the S1.1 review branch.

7. Specified

Evaluate

Held-out, adversarial and contract tests produce immutable receipts outside candidate bytes.

8. Missing

Release

Attestation binds candidate digest, receipt set, source commit, policy and approval.

9. Missing

Project

Release-scoped lexical, vector, graph and catalog projections are disposable and rebuildable.

10. Partial verified

Serve agents

REST/MCP and context retrieval exist; typed domain operations and verified-release enforcement remain.

The system does not yet support this workflow end to end. A client launch corpus can be explored with harnesses today, but production ingestion should wait for source identity, parser spans, candidate persistence and evidence enforcement. Otherwise useful discoveries will become untraceable content rather than governable domain knowledge.

SME knowledge codification

The correct product is a structured interrogation and ratification flow, not an unconstrained chatbot that writes directly to a pack.

Profile

Establish expertise

Function, market, therapy area, evidence access, decision authority and confidence calibration.

Probe

Test distinctions

Counterexamples, boundary cases, differences between similar terms, and when a rule fails.

Challenge

Expose disagreement

Competing hypotheses, missing evidence, market variation, temporal validity and dissent.

Ratify

06

Domain pack shape and storage

A domain pack is a governed source product compiled into an immutable runtime product. Search indexes and graphs are projections, not truth.

Source pack
Ontology, terminology, claims, decision definitions, operational questions, process playbooks, metric/table contracts, policies, agent views and eval cases.
Private Git repo at immutable SHA
Compiled candidate
Deterministic normalized artifacts, exact payload inventory, manifest v2, candidate digest and integrity seal. No timestamps, eval results or local paths inside.
Content-addressed object storage
Evaluation receipts
Suite digest, candidate digest, runner, environment, results, failures, coverage and policy verdict. Append-only and external to candidate bytes.
Governance DB / registry metadata
Verified release
Candidate digest bound to passing receipt set, source commit, release policy, approval, tenant and compatibility constraints.
Artifact registry
Projections
OpenSearch/vector chunks, graph adjacency, catalog rows and runtime caches, all scoped to tenant and release.
Disposable data-plane stores
Files

Semantic source and immutable builds

Human-reviewable YAML/JSON plus digest-addressed compiled candidates. Raw client documents remain outside Git.

Relational

Workflow and governance state

Sources, versions, runs, candidates, approvals, Deltas, audit, receipts, releases and access policy.

Search and graph

Rebuildable acceleration

Metadata prefilter, semantic rank and lineage traversal. No agent reads storage directly.

07

How agents consume context

Agents call a typed contract over a verified release. The runtime resolves ontology, exact rules, evidence, documents and structured data without exposing storage topology.

Resolution

Resolve intent to context keys

  • resolve(term, scope) returns canonical entities, aliases and ambiguity.
  • get_definition(id) returns governed meaning and applicability.
  • get_rule(id) returns exact policy or decision logic with evidence.
  • search_context(query, filters) uses metadata prefilter before semantic rank.
Structured analytics

Serve schema and metric contracts

  • get_metric(name) returns formula, grain, filters, exclusions and authority.
  • get_table_schema(table) returns columns, semantics, freshness and allowed joins.
  • query_contract(id) returns governed query requirements, never raw rows in prompt context.
  • explain_context(result) returns sources, release, evidence and resolution trace.
Current limitation: REST/MCP and catalog retrieval are real, but the complete typed serving contract above, verified-release-only loading, source-span evidence and release-scoped projections are not yet implemented. Agents should not be presented as consuming production-grade context until S1.2/S1.3 and B7/B11 are complete.

Backend-first build sequence

The old week-based five-phase roadmap is replaced by dependency-gated units. This moves the programme from specification churn to demonstrable vertical slices.

Gate S1.1 and close candidate integrity

Complete read-only review of 4eead82, resolve the remaining cleanly stated finding if any, and update the authoritative status only after full verification.

Now - blocking

Build S1.2 then S1.3

Verify before load, remove glob-based trust, then produce immutable eval receipts and separate release metadata from candidate bytes.

Step 1

Freeze the schema and source contracts

Add schema registry, PackSource, ArtifactRegistry, source/evidence, semantic, analytics, evaluation and release contracts in ontowiz-spec.

Step 2 / B0-B1

Build the managed source and parser substrate

Source registry, immutable versions, rights/access, F0.4A parser boundary and optional rich digitization adapters. No model calls in parsing.

B2-B3

Build extraction, evidence and reconciliation

Durable runs/stages/candidates, decision-question kernel, exact evidence assertions, resolver strategies, disagreement and coverage.

B4-B8

Activate SME Forge and Grill Me

Persistent interview sessions, adaptive probes, candidate ratification, gamified contribution, Deltas and eval generation over the same backend.

B9

Complete eval, release, projections and typed serving

Held-out suites, release attestation, rebuildable OpenSearch/vector/graph projections and verified-release-only agent contracts.

B10-B12

Prove one Launch Control Room vertical

Ingest a rights-cleared corpus, derive questions and decision playbooks, ratify with SMEs, bind operating data, replay held-out launch rooms and publish one verified release.

Reference vertical
Definition of meaningful progress: every delivery loop must end with a working behavior, can-fail tests, an immutable review SHA and a verified status update. Mini-spec completion alone is not progress against the client workflow.
09

Settled decisions and live risks

These replace the open-decision table in the previous blueprint.

SETTLED: modular monorepo, three deployables

No microservice split now. Control, build and data planes are package and deployment boundaries inside one platform repository.

SETTLED: client packs outside the platform

Shared base packs and private client overlays are external PackSources pinned to immutable commits.

SETTLED: typed contract, not storage access

Agents call REST/MCP/SDK operations over verified releases. Search, vector and graph stores are replaceable projections.

SETTLED: SME output proposes, governance commits

Chat, games and extraction never modify an ACTIVE pack. They produce candidates, findings, eval cases and Deltas.

RISK: authoritative status is stale

PROJECT_STATUS.md still says S1.1 is awaiting first implementation review and does not record 9d52b47/4eead82. INT must reconcile it after verdict.

RISK: implementation branches are stacked and unmerged

S1.1 and D0.1-D0.4 exist on isolated branches. Their presence in local refs is not equivalent to integration or release.

RISK: known fixture integrity failure

The historical commercial pack includes a stale pack.sig fixture failure. It must be handled in its own scoped migration/reseal unit, not hidden in S1.1.

RISK: prototypes can overstate readiness

The control-plane and architecture HTMLs use synthetic/mock state. Their role is experience validation, not evidence of backend completion.

Do not do these next: do not build a second ontology model, add direct sibling-repo dependencies, make Docling mandatory, use similarity as evidence, let an LLM commit a pack, put mutable eval data inside candidate directories, or build a polished Launch UI over mock backend state.

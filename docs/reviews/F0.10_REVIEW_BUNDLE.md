## 4. Projection / semantic diff

No pack is recompiled and no artifact changes; F0.10 changes what the **door** does with an
existing pack. The observable API diff:

| Surface | Before | After |
|---|---|---|
| MCP tools | `context/get`, `pack/list`, `pack/query` | + **`ctx/hydrate`** (the tool the L3 prompt already advertised) |
| MCP `context/get` `trust` | `pack`, `confidence`, `lifecycle_floor` | + `artifacts_used`, `backing_deltas`, and `tokens_estimate` alongside — **now equal to REST** |
| REST | no hydrate route | + **`POST /v1/hydrate`** |
| Hydrating a gated/unknown section | silent empty **success** | typed refusal (MCP `{"error": "section not servable: …"}`, REST **404**) |
| Tag-sliced context | guardrail/override/data-quirk silently dropped | safety kinds survive the tag filter (still lifecycle-gated) |

REST response keys are **unchanged** — REST was the reference shape and MCP moved to match, so
the frontend client needs no change.

## Reviewer's attention is specifically invited on

1. **The scope addition** — `POST /v1/hydrate` is not in the card text. Accept or reject.
2. **The non-leaking refusal.** It is a deliberate trade: a caller cannot tell "you may not have
   this" from "this does not exist", which is worse for debugging and better for confidentiality.
3. **The carve-out's blast radius.** It is scoped to the tag filter within one loaded pack. The
   shipped `commercial_analytics` pack contains zero `ALWAYS_INCLUDED_KINDS` artifacts (1
   `entity_registry` + 23 `decision_heuristic`, verified), so no shipped slice count moves and the
   new behavior is exercised only on artifacts built inline in tests. That also means this safety
   rule has **never been exercised by real pack data** — worth a note against V1–V4.
4. **§3.1** — the pre-existing red is a lane-wide blocker awaiting an INT decision, not an F0.10
   defect. Nothing can reach the completion gate until it is dispositioned.

# Onto_Wiz — Strategic Review (July 2026)

**Method.** Nine parallel agents deep-read the entire repository (packages, legacy src, ontology content, all three generations of vision docs, LEAD_REVIEW, spec_raw, docs/ADRs, frontend, quality infrastructure, ops). Three independent strategists — product, engineering, and market/defensibility lenses — then proposed strategies. Their fifteen strongest positions were each attacked by three adversarial reviewers with repo access. What follows is the synthesis of what survived. Tests were actually re-run in a clean environment as part of the review: all 526 tests pass; the codebase is genuinely green, not claimed-green.

---

## The verdict in one paragraph

Onto_Wiz is a well-engineered, honestly-built **headless engine with no product on top of it and no validated content inside it**. The engineering discipline is real (526 passing tests, triple-enforced governance invariants, genuine red-team fixes in the code). But the two things the pitch rests on are both currently hollow: the "SME-validated pharma judgment" was in fact authored by an autonomous Claude agent (every artifact carries `sme_id: ''`), and the flagship +0.308 agent-lift number comes from a dev-authored, partially circular eval suite — and the currently served pack (0.3.0) ships with `eval_cases: 0, gate_passed: false` anyway. Meanwhile the SME-facing UX runs on an unauthenticated legacy backend whose approvals are stored in in-memory dicts and evaporate on restart, and nothing has ever been deployed to a live URL. The strategy that survives adversarial review: stop framing this as ontology management, ship the governed judgment-pack loop as one unified product, and spend the three months getting **real SMEs to validate real content on a real URL** — because until that happens, the moat this product claims does not yet exist.

---

## Q1 — What is the genuinely defensible core value?

All three strategists converged, and the position survived attack with one crucial correction.

**The defensible thing is the closed loop, not any component:** SME judgment → governed Delta → compiled Domain Pack → eval gate → measured agent lift. No component alone is a moat. The CTX codec is commodity context plumbing. The Tier-B "secret sauce" is 1,947 LOC — the "miner" is 67 lines of two regexes (its own docstring advertises "9 extractors + InterviewAgent" that do not exist). The taxonomies are LLM-regenerable. Protégé/PoolParty sell schema tooling; LLMs now draft OWL for free. What nobody sells is **verified, liability-bearing, org-specific decision rules with a measured lift receipt** — and the harness to keep that claim honest release after release.

**The critical correction from the adversarial pass:** the review's market skeptics demonstrated that the content moat is currently *prospective, not actual*. The 20 priority-ordered triage rules in `commercial.yaml`, the 22-account gold set, the eval suite — all were generated by Claude (docs/AUTONOMOUS_AGENT_PROTOCOL.md assigns them to the "ATLAS" agent), no SME has validated a single rule, and the +0.308 lift is a retrieval-shaped test where each `must_contain` answer term is guaranteed present in the pack. Every strategic "VALIDATED" verdict in the vision corpus is ChatGPT grading its own homework.

**Implication — this is the single most important strategic fact:** the moat is not something to *protect*; it is something to *earn*, SME-hour by SME-hour, starting now. Which means the 3-month pilot with real ZS SMEs is not a milestone — it is the existential test of the entire thesis. The machinery to earn it (governance invariants, compiler, eval harness, benchmark protocol) genuinely exists and works. That machinery plus SME access is the business.

## Q2 — Kill / Keep / Rebuild

### Kill

- **The "organisation ontology management" framing itself.** This position survived all three attacks. No vision doc describes it, the repo's own prior review warns against ontology-as-product (spec_raw.md:157, 599), there is no graph editor (reactflow installed, never imported), and content is n=1 domain. Chasing it means competing with Protégé/PoolParty/Palantir solo. The honest reframe that still serves your stated users: *seamless creation and management of governed judgment, for domain SMEs (create, via capture) and curators (manage, via review/approve/recompile)* — not a generic taxonomy editor.
- **~10,000 LOC (78%) of ontowiz-ctx** never imported by any product path (packer/, codebase.py, analytics, cli, mcp_server, agent/) — verified by import grep. You currently ship your least-tested package (3 smoke tests) as the client-visible Tier-A surface.
- **The Tier-B secrecy programme as an IP strategy** (sealed builds, encryption roadmap, license binding). Survived attack twice. Keep the 62-line boundary check purely to keep LLM dependencies out of the deploy image. Zero engineering hours on code secrecy this year — the secret is the content and eval corpus, and even that must be earned first (see Q1).
- **Process harness beyond four tools.** Survived attack decisively. slop_checker has 38 standing findings and no staged mode (so every commit bypasses it); quality_gate fails the repo in blocking CI; the frontend "gate" runs in no CI job. A harness that is red on its own tree while claiming green trains you to ignore it. Keep: ruff, mypy, pytest (≥85% on *all shipped code*, including ctx core), check_boundaries. Retire: slop_checker, quality-gate/, cathedral-keeper for new code, the second CI workflow.
- **Marketplace features ahead of inventory** — pack diff, telemetry stats, Elo ForgeRating polish, for a catalogue of exactly one pack.
- **Repo archaeology:** checked-in `build/` duplicate source trees, the 126KB session transcript at root, the Feb four-team simulation corpus (~2,600 lines), Gen-1/Gen-2 vision docs, triplicated blueprint, empty dirs, unused frontend ui/ primitives.
- **Pack 0.2.0/0.3.0 as currently shipped** (`gate_passed: false`) — re-gate or delete; see Rebuild.

### Keep

- **ontowiz-spec + ontowiz-runtime + ontowiz-serve** — the governed serving engine. api.py at 100% coverage, triple-layer lifecycle enforcement (UngovernedTransitionError → bridge.py → runtime gate()), path-traversal-guarded PackRegistry, JWT/RBAC, SQLite seam. Verified sound and deployable.
- **The eval / agent-lift benchmark machinery** (commercial_eval_suite.py, temp-0 with/without protocol) — this is the sales instrument, once its circularity is fixed with SME-authored held-out cases.
- **The Delta governance invariant** (transitions only via APPROVED deltas) — the enterprise trust story.
- **The pharma content as a *draft*** — commercial.yaml's 20 rules + forecasting's 4, the oncology files, metrics.yaml, the gold set — reframed honestly as high-quality Claude-drafted candidates awaiting SME validation. (Fix the Germany/US payer-mechanics bug before any pharma SME sees it: 340B/ASP/copay-accumulator logic on German hospital accounts will kill credibility in one demo.)
- **The frontend** — the game and curator flows are polished UX designs wired to the wrong backend; the catalog slice is properly tested. Rewire, don't rewrite.
- **ontowiz_ctx.core** (~2.8k LOC actually consumed) — fold into ontowiz-runtime and bring under the coverage gate.
- **verify-audit discipline, ADR-015 loop, PROJECT_STATUS.md as single source of truth** — the anti-overstatement culture demonstrably caught real CRITICALs. It earns its keep once slimmed.

### Rebuild

- **Governance persistence — the single highest-priority engineering unit.** Survived all attacks. Every Delta, approval, audit entry and contribution lives in in-memory dicts (`stores.py` admits it: "will be replaced with persistent storage") while catalog *comments* got SQLite. An SME's approval currently evaporates on restart; a governance product whose governance doesn't persist is a demo. The db.py seam already exists — this is days of decisive work. One caveat from the attackers worth heeding: persist it *where the deployed product runs* (ontowiz-serve), not in the legacy layer.
- **One unified backend.** Port the SME surface into ontowiz-serve under its existing JWT/RBAC. **Scope correction from the adversarial pass:** this is not "port two endpoints, days of work" — the frontend consumes ~14–18 src-only endpoints (sessions/capture, review queue, approve/reject/escalate, audit log, contributors). Budget 2–3 weeks, port the endpoint surface deliberately, then delete src/ and verify-audit gate 6. Today curator approvals run on an auth-less server attributed to the literal string `'curator'` — the audit trail is fiction.
- **One unified frontend.** Single nav (the catalog page currently isn't linked from anywhere), single auth, and a link from each delta under review to the catalog artifact it modifies — the two halves of the product currently never meet.
- **The eval gate as a hard compiler check.** compiler.py must refuse to emit a pack with `gate_passed: false`. Re-run the suite against 0.3.0. (The attackers showed "violating its own gate" is rhetorically inflated — PROJECT_STATUS honestly records the deferral — but the substance stands: your differentiator is detached from your shipped artifact, and the fix costs days.)
- **Compile-on-approve as a product feature**, not scripts/run_living_loop.py — approved deltas trigger recompile + eval + lift measurement behind a curator button.
- **LLM-assisted extraction with a human promotion gate** — Claude proposes candidate rules + paired eval cases from real ZS decks/transcripts into the review queue; never auto-promotes. The parsers already exist in src/knowledge. This replaces the 67-line regex "miner" and is the only credible scale answer to the founder's own red-team objection ("an elegant expert system with a modern coat of paint"). The attackers' refinement: the Forge game backend already exists and its submit contract is precisely the gold-eval supply channel — so don't build the game UI, but do route mined candidates through its existing contracts.

## Q3 — The 12-month thesis and the architecture that serves it

### Thesis

**Onto_Wiz is an eval-gated domain judgment pack factory, sold for the next 12 months exclusively through ZS pharma engagements.** The pack is the product; the lift receipt is the pricing and trust mechanism; the platform is the factory that keeps packs alive. The pitch is one number: *"your agent answered 18/26 brand-diagnosis questions blind, 26/26 with the pack — here is the eval receipt, and here is the named SME who approved every rule it used."*

Foundation models are the tailwind, not the threat: they make agents ubiquitous and undifferentiated, which makes governed, evaluated, SME-signed domain judgment the scarce input — and the MCP serving rail is already built. One domain, deep. "Generalising beyond pharma" means re-authoring content, not reconfiguring code (the review verified this directly), so breadth before month 12 is self-harm.

**Month-12 success looks like:** the full loop live in production (capture → persistent governance → auto-recompile → eval gate → catalog); a 300+ case eval corpus where the held-out cases are SME-authored, not dev-authored; 3–5 client-layered pack versions each with a with/without lift measurement; 5+ named SMEs whose approvals survive a server restart and appear in a real audit trail; one live ZS engagement consuming the pack via MCP; a second adjacent pack (forecasting or market access, same SMEs) proving the factory runs twice. Explicitly deferred: non-pharma domains, the Forge game UI, marketplace features, encryption/licensing, multi-tenancy, Postgres.

**The kill test (be honest about it):** if by month 4–5 real SMEs will not engage with the capture/review loop, or an arm's-length pharma stakeholder won't accept the lift receipt as evidence, the thesis is falsified — the founder's own red-team objection stands, and the asset to salvage is the governance/eval engine as consulting tooling. One attacker's caveat worth carrying: a ZS colleague pre-endorsing gamification "110%" is not validation; seek at least one arm's-length signal (a client-side user, or a paid engagement line-item) inside the 12 months.

### Architecture

One deployed FastAPI app (**ontowiz-serve**) owning capture, governance, review, catalog and context serving, over three libraries: **ontowiz-spec** (contracts + lifecycle invariants), **ontowiz-runtime** (context assembly, PackRegistry, the folded-in ctx core codec with real tests, and the SQLite governance tables: deltas, approvals, audit, contributions), and **ontowiz-core** reduced to the Delta/bridge governance engine (the pharma-game types die with src/). **ontowiz-factory** becomes an offline pipeline — parse → LLM-propose → human review → compile → eval — the only place an Anthropic key exists; it emits signed pack files, which remain the unit of deployment. The serving path stays key-free. One Next.js app, one auth model, one API client. SQLite now; Postgres only when a second tenant forces it. CI: ruff + mypy + pytest (85% on everything shipped) + boundary check + the frontend vitest gate actually wired into CI. Net: ~23k package LOC + 3.6k legacy shrinks to roughly 12k product LOC — a system one person can hold in their head and keep green, which is the only architecture a solo dev can sustain.

Exit criteria: live URL; passing gated pack; ≥100 eval cases of which ≥25 SME-authored; ≥50 SME-approved deltas from mined candidates; one lift receipt an outsider would accept.

4. **"The project violates its own completion gate" → rhetorically inflated.** PROJECT_STATUS honestly documents 0.3.0's unmeasured lift as a deferral. The substance (differentiator detached from shipped artifact) stands; the accusation of dishonesty does not.
5. **"The Forge game is pure theatre" → its backend contracts are the right supply channel.** Don't build the game UI; do route mined candidates through the existing submit/consensus contracts.

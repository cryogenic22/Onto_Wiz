1Executive verdict

Yes — the repo is genuinely becoming a harness for governed domain packs, but it is one-sided. The consume side (govern → compile → seal → lifecycle-gate → serve with a trust envelope → measure agent lift) is real, tested, and demonstrated end-to-end on one authentic pharma-commercial pack. The produce side — capture from SMEs and documents, consolidation across sources, an authoring path a client team could operate — is the thinnest part of the codebase: mining is a two-regex stub, the LLM extractor is dead code, and every artifact that has ever shipped was hand-authored YAML run through Tier-B Python by the core team. The July platform pivot (ADR-018/019, S1.x specs) targets exactly the right defects, but is so far documentation plus zero implementation.

What is real

A signed†, versioned commercial_analytics pack (24 governed artifacts, lifecycle history, audit delta-ids) served through a governance gate that provably never exposes DRAFT knowledge, with a trust envelope carrying backing deltas — behind 218 package tests (98.49% cov), 312 legacy tests, ~75 FE tests, and a six-gate verify-audit that passed cold. +0.308 measured agent lift on v0.1.0 (see honesty note).

What is thin

Capture & consolidation. No SME interview agent, no document→knowledge path (parsers exist; extraction is a placeholder), no dedup/conflict machinery outside dead code, one pack family ever compiled (n=1), multi-pack composition is dead schema (PackLayer/depends_on never read), and governance approval in the live pipeline is an unauthenticated in-process field-write.

What it means

A guided pilot could consume today; no team can self-serve author. First real usage is ~3 milestones (~8–10 unit-weeks) away by riding the already-specced S1.1→S1.3 + F0.3 + control-plane Slices B/D — no new roadmap needed. The bottleneck is the review gate’s throughput, not the architecture.

UC1 · Brand-analytics agents ✓Demo-able in days

The one proven slice. The compiled pack measurably lifted a mid-tier model on root-cause diagnosis (+0.308 term-adoption lift, 26/26 with-pack at temp 0), the knowledge is genuinely expert (the discriminations a capable model misses blind: copay-accumulator vs price war, pathway exclusion vs guideline shift, 340B erosion), and /catalog can browse and review it live.

  • Missing: any numeric grounding — the pack classifies narratives but holds no MetricDefinition bound to data; ontology/metrics.yaml (23 metrics: TRx, NBRx, PDC, pa_reject_rate…) is authored but uncompiled and unbound. The latest pack version ships un-evaluated (gate_passed:false).

UC2 · Market-research agents, structured + unstructured fusion ◔Capture seam broken; fusion design-stage

The trust primitives are exactly right and already servable — SourceContract (trusted_for / not_trusted_for / known_lag / reliability), DataQuirk, JargonMap are precisely the vocabulary for fusing tracker/Rx data with verbatims. The parser stack for MR source types exists. But:

  • Unstructured side: transcripts/verbatims cannot become pack artifacts today except by hand-authoring YAML — mining can’t read them, the LLM extractor is dead code, there is no ingest API.
  • Structured side: no connectors, no query engine, no semantic-layer execution anywhere; TableContract/JoinContract/QueryReceipt are schemas in the pivot docs only. Both halves of “fusion” are unbuilt; only the serving spine between them is real.
  • Unowned design question (make-or-break): if the agent runs SQL itself, who verifies the query matches the governed MetricDefinition? And can the one-line-BODY format ever carry table/join contracts? These need an explicit decision before the fusion roadmap is credible (§6 proposes where they land).
  • Shortest honest demo (~2 weeks): swap mining’s regex internals for an LLM extraction step behind the same mine_to_deltas contract (reuse PatternExtractor’s prompt/dedup + the parser stack); 3–5 mock IDI/ATU transcripts → mined candidates → curator approves → compiled market_research pack; structured data stays agent-side (DuckDB/SQLite fixture) governed by the pack’s SourceContracts and metric semantics — platform-side fusion stays correctly deferred to B11.

UC3 · MLR content review ✕Paper excellence, zero executable path

The design is the best MLR spec this codebase could ask for — the Auravia fixture has typed claim propositions, support assertions with source spans down to table+row, risk-bundle coupling, semantic invariants, prohibited transformations, and a preflight contract that structurally cannot return APPROVED. That posture (assist, never approve) is the differentiator MLR teams respond to. But:

  • No Claim/SupportAssertion/RiskBundle kinds exist in the 19-kind registry; the fixture self-declares production_eligible:false and is referenced by zero code; the frontend MLR demo is a hardcoded switch statement. Nothing computes.
  • Even the working spine has compliance-disqualifying holes for this audience: unenforced always-include for guardrails, unauthenticated attribution, seal unverified at load, no Part-11-shaped e-signature discipline, no integration story with systems of record (PromoMats-class claim libraries) or the human-reviewer workflow product.
  • Shortest demo-grade path (~2 weeks, labeled synthetic): add 3 artifact kinds following the established pattern, hand-port 5–8 Auravia claims/risk-bundles into a compilable mlr_reference pack, build a 15–20 case suite with must_not_contain: APPROVED as the signature invariant. Compliance-grade is a separate, months-scale program — never conflate the two in front of a client.

UC4 · Omnichannel decisioning Named, unanalyzed until now

A first-class workload in your own platform reference (frequency caps, next-best-action, suppression windows) and a control-plane mock scenario. Structurally it is UC1’s shape (heuristics + guardrails + metric semantics) plus action governance — the ExceptionRule/Guardrail kinds fit, and it should ride UC1’s pack rather than get its own lane until after M3 (§9).

6The context-layer deliverable — target design

What a client team should receive, and how it scales across domains, functions, therapy areas and clients without a rewrite. Four rules, each grounded in schema that already exists in the repo — this is a finishing plan, not a new architecture.

Rule 1 — Coordinates, not hierarchies

The address space for all knowledge is the 9 existing tag dimensions (therapy_area · drug · indication · data_source · analytics_domain · task_type · geography · function · client) — not a directory taxonomy. Function slicing through tags already works through the real serving path (with measured slice-vs-full token leanness); keep function intra-pack, never a pack species. Make Tag.parent real (oncology→NSCLC rollups) or delete it — today it is dead schema a contract reader will believe.

Rule 2 — Two pack species, and resolution instead of merging

BASE domain packs (commercial_analytics today; market_access/medical_affairs/HEOR next — compilable from the 11 already-written ontology/domains modules) and thin OVERLAY packs (therapy-area, client, engagement) that contain only additions/overrides and declare depends_on pins + PackLayer precedence (10/50/100 per the blueprint — the schema has existed unread since the manifest was written).

The composition decision this repo should commit to (ADR-worthy): overlays are resolved at compile time by the Step-5 resolver into one digest-addressed, sealed, resolved release. The runtime always serves exactly one pack per agent. Serve-time multi-pack merging is rejected: it multiplies the conflict, eval-validity and provenance surface — and it means the served composition was never the thing the eval gate measured. Compile-time resolution preserves the repo’s single best invariant: the served thing IS the eval-gated thing.

Rule 3 — One governance write model

Blueprint Open Decision 4 is still unresolved in code, and it is the riskiest hole in the platform: today the legacy in-memory DeltaStore (routing/SLAs/audit — wired only to the frozen app), the factory’s unauthenticated in-process approval, and the durable-but-endpointless GovernanceStore all coexist. Decide: GovernanceStore (ontowiz-runtime/governance.py — durable, transactional, restart-survival-tested) becomes the single system of record. The factory bridge writes through it; approvals require an authenticated principal from the existing JWT/RBAC layer; serve exposes read-only GET /v1/deltas/{id} so every backing_delta in every trust envelope finally resolves to who approved what, when, why.

Rule 4 — Receipts outside the artifact

Exactly as S1.3 specs it: eval receipts are append-only records keyed by candidate_digest, never written into the pack and resealed (today’s benchmark literally mutates the candidate it certifies). Combined with S1.1 (deterministic, digest-addressed compile with input/output inventories) and S1.2 (verify-before-load with typed refusal), the deliverable becomes pinned, verifiable, and externally receipted.

8The consolidation gap — the word in your mandate

“Consolidating the domain packs” is the one capability with no owner, no design, and no milestone anywhere in the program. Everything built so far assumes a single hand-authored source per pack. The moment two SMEs, three engagement decks, and a transcript batch feed the same domain, you need: dedup of near-identical candidates, detection of contradicting heuristics (same trigger, different verdict), scope-collision handling, cross-layer override validation, and a merge/supersede policy with an audit trail. The blueprint named four conflict classes and a Consolidation agent — both undesigned then, both unbuilt now. The only dedup logic in the repo (0.8-Jaccard) sits in dead code.

Where consolidation should live (two insertion points, both in existing seams):

  • Curation-time (intra-pack): a candidate-set consolidation pass between mining and delta-proposal — dedup + contradiction detection over DRAFT candidates, surfacing conflict pairs to the curator queue rather than silently proposing both. Home: ontowiz-factory, consuming the same artifact contracts; the SME “Grill Me” plan (GM-series) should submit into this pass, not around it.
  • Compile-time (cross-pack): the Step-5 resolver’s conflict surface (§6 Rule 2) — overlay-vs-base override legality, same-id collisions, terminology conflicts across depends_on inputs. Fail loud; a human confirms resolution; the resolution itself is a governed delta.

Sequencing: a minimal curation-time pass belongs in M3 (the first moment pilot-authored knowledge arrives); the cross-pack surface arrives with the resolver in M4. Until then, say “governed authoring,” not “consolidation,” in any external narrative.

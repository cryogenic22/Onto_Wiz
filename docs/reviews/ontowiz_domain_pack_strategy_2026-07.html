Strategic architecture

A domain pack should be a governed, executable context product.

It is not a folder of prompts, an ontology alone, or a vector index. It is a versioned semantic product that binds meaning, evidence, policy, analytics, agent contracts and evaluations into one reproducible release. The same governed core should serve MLR, market research, analytics, forecasting, segmentation and brand planning through task-specific views rather than duplicated agent-specific knowledge bases.

Primary recommendation

Separate modules from layers. Modules describe capabilities such as claims, metrics or forecasting. Layers describe precedence and applicability such as market, therapy, brand, client and engagement. Mixing them creates unmanageable overrides.

01

Executive decision

The platform should optimize for governed reuse, precise applicability, verifiable releases and task-specific context resolution.

One core

Shared semantic truth

Brand, indication, audience, claim, metric, data source and policy identities are defined once and referenced across functions.

Many views

Agent-specific context products

Each agent receives the minimum eligible slice, typed operations and failure rules needed for its task.

Immutable releases

Change creates a new version

Source, policy, metric or SME corrections produce Deltas, targeted re-evaluation and a new release, never in-place mutation.

Measured value

Accuracy must be attributable

Held-out comparisons prove where the pack improves correctness, restraint, traceability and task completion.

Strategic unit of reuse: use a shared pharma-commercial base, market-policy modules, therapy and brand overlays, client operating context, and task views. Do not create six disconnected packs for six agents; they will drift on the same claims, metrics, audiences and definitions.

03

The domain pack product model

Five representations are needed. Each has a different owner and lifecycle; treating them as one folder creates accidental coupling.

1. Evidence plane
Immutable source versions, rights, access class, exact spans, structured source snapshots and extraction provenance. Raw client documents remain outside Git.
Client systems + object store + source registry
2. Semantic source pack
Human-reviewable canonical artifacts, relationships, applicability, policies, agent contracts and evaluation cases. Approved semantic source is pinned to an immutable commit.
Base-pack and private client-pack repositories
3. Compiled candidate
Deterministically resolved layers and dependencies, canonical bytes, exact inventory, candidate digest and integrity seal. No timestamps, mutable eval summaries or local paths.
Content-addressed build storage
4. Verified release
Candidate digest bound to immutable evaluation receipts, approval, compatibility, tenant, source commit and rollback target. This is the only eligible runtime input.
Artifact registry + release metadata
5. Runtime projections
Lexical, vector, graph, catalog and cache views built from one release. They are disposable acceleration structures, never independently editable truth.
Per-tenant data plane
Identity

Content-addressed and reproducible

The same approved source commit, dependencies and compiler produce the same candidate bytes and digest.

Authority

Release is a policy decision

Passing tests is necessary but not sufficient; the attestation records accountable approval and eligible scope.

Runtime

Serve a projection, trace to truth

Every answer moves backward from response to release, artifact, review, source span and immutable source version.

Override rule: a higher layer may narrow eligibility, add local context or replace an explicitly overridable artifact. It must never silently broaden a label, claim, privacy, safety or regulatory permission. Correctness-critical conflicts fail compilation.

Recommended source-pack structure

The repository remains human-reviewable, but every file compiles through the schema registry. Directory names are modules, not runtime APIs.

Mandatory artifact envelope

Every governed object carries its context

  • Stable ID, kind, schema and semantic version.
  • Owner, review authority and lifecycle.
  • Tenant, market, brand, indication, audience, purpose, channel and time applicability.
  • Exact evidence references, effective/expiry dates and supersession links.
  • Access class, creation method, evaluation links and release identity.
Fail-closed defaults

Absence is not global permission

  • Missing applicability on critical artifacts is an error.
  • Unresolved references and duplicate identity fail compilation.
  • Expired evidence cannot support a claim.
  • Undeclared joins and causal interpretations are prohibited.
  • Synthetic fixtures cannot enter production.

Agent context views

Each view defines decisions, required modules, typed operations, critical failures and feedback contribution. Underlying artifacts remain shared.

Preflight promotional content and explain findings; never represent approval.

Task-view rule: each agent contract pins the release, module set, applicability filters, required evidence, structured tools, output schema and abstention behavior. The runtime resolves this view; the agent never chooses arbitrary files.
07

Route context by failure mode

Accuracy improves when the serving mechanism matches how the answer can be wrong. Vector retrieval is only one route.

Wrong equals defect
Deterministic context

Definitions, label constraints, claim semantics, formulas, joins, privacy and guardrails are compiled and injected exactly.

Missing equals failure
Semantic retrieval

Research excerpts, planning rationale and examples use metadata prefilter then semantic rank, retaining release and span identity.

Bad figures equal failure
Structured query tools

Metrics and forecasts are schema plus governed query contracts. Agents call approved data products; raw rows do not enter prompts.

Ambiguity equals risk
Ontology resolution

Terms resolve through IDs, approved aliases and applicability. Probabilistic mappings remain candidates.

Reasoning can overreach
Decision and evidence graph

Observations, hypotheses, confounders, choices and actions remain distinct typed objects.

Unknown is legitimate
Typed abstention

Not found, stale, blocked, conflicting, insufficient and access denied are first-class responses, not successful empties.

09

Context evolution and versioning

Continuous improvement should compound knowledge without erasing historical truth or making released behavior irreproducible.

Observe a trigger

New source, label update, data revision, agent failure, SME correction, planning outcome, forecast error or segment instability creates an immutable event.

No pack mutation

Run impact analysis

Traverse source, artifact, dependency, agent-view and release lineage. Mark typed staleness and accountable owners.

Derived state

Create candidates and a Delta

Extraction or SME curation produces typed alternatives, exact evidence, critic findings, compatibility intent and regression cases.

Proposed change

Review and materialize approved source

Approval materializes a new immutable source commit; rejected and dissenting alternatives remain auditable.

Truth changes

Compile and evaluate

Impact selects focused tests; shared critical modules also run full affected agent-view suites. Results become immutable receipts.

Candidate immutable

Release, project and monitor

Publish a new attestation, rebuild release-scoped projections, canary consumers and retain rollback.

Controlled adoption
Patch

Compatible correction

Evidence link, clarification, typo or case addition with no changed contract or applicability.

Minor

Additive capability

New metric, claim, segment, optional operation or relationship without altered existing meaning.

Major

Breaking semantic change

Changed definition, formula, applicability, removal, schema break or interpretation.

Typed staleness: source expired, source superseded, label/policy changed, SME review overdue, dependency changed, evaluation too old, projection model obsolete, release superseded and artifact withdrawn are distinct states with owner and remediation.
10

Architecture for solution scale

Scale comes from stable contracts, immutable releases and rebuildable projections, not one large repository or vector index.

Platform repository

One modular monorepo

Spec, core, factory, runtime and serve evolve together with enforced tiers and three deployable planes.

Pack repositories

Shared base plus private overlays

Base IP is reused. Client context is separately pinned and never coupled to a platform release.

Artifact registry

Tenant-specific verified releases

Content-addressed storage first; OCI-shaped distribution and signed provenance after the kernel is proven.

11

Quality and evaluation spine

Judge critical failure prevention and attributable agent improvement, not artifact count or one aggregate pass rate.

Structural

Can it compile safely?

Schema, IDs, references, applicability, deterministic bytes, inventory and migration.

Grounding

Can every claim be traced?

Exact spans, authority, support relation, validity, contradiction and access.

Task

Does the agent perform?

Golden cases, calculations, abstention, adversarial traps and output schema.

Critical

Does it prevent severe errors?

MLR, privacy, tenant isolation, numeric correctness and causal overclaim.

Agent lift: compare the same agent with and without the verified pack on held-out cases. Report accuracy, grounding, abstention, critical errors, uncertainty, latency, tokens and cost. Aggregate improvement never compensates for critical compliance, privacy, isolation or numeric failure.

Second-consumer gate
Definition of done

Production-ready pack

  • Source commit, dependencies and schemas pinned.
  • References, applicability and critical conflicts validate.
  • Candidate bytes deterministic and exact-inventory verified.
  • Task and critical suites have immutable receipts.
  • Attestation and rollback target exist.
  • Typed views serve only eligible traceable context.
  • Isolation and silent-empty tests pass.
Stop conditions

Do not scale when

  • Agents read files or storage directly.
  • Similarity is treated as evidence or identity.
  • Mutable evals live in candidate bytes.
  • Client content is coupled to platform code.
  • One view's correction silently changes another.
  • Critical errors hide in aggregate pass rate.
  • Behavior cannot be reproduced from lineage.

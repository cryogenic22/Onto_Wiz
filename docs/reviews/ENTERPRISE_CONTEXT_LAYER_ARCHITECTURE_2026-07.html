0How to read this

This report answers one question in two registers: what should an enterprise AI context layer physically look like — the folders, the graph, the databases, the vector store, the step-by-step runtime path — and how does the design being built here map onto that. The two registers run in parallel throughout. Where the reference model and the current build diverge, the divergence is named with a status badge rather than smoothed over, because the difference is the actionable part.

The framing borrows the status vocabulary the platform already enforces on itself: verified, submitted, specified, design-fixture and missing are not interchangeable. Most of the ambitious architecture in Part II is SPECIFIED or ROADMAP; the BUILT core is deliberately narrow. Stating that plainly is the point of the exercise — a context layer that overstates its own maturity is the failure mode this design was built to avoid.

Scope
This is an architecture reference, not an implementation spec. It cites concrete files and lines so any claim can be checked against the tree (Appendix), but it does not propose code. Vertical examples are illustrative; "MR chatbot" is read here as a field-facing, MLR-governed medical/market assistant.

1The problem, stated precisely

An "AI context layer" is the machinery that puts the right slice of governed domain knowledge in front of an agent, at the right resolution, provably, inside a token budget, at request time. Every word in that sentence is a design constraint:

  • Right slice. A pharma brand agent asked about a launch does not need the entire company knowledge base; it needs a bounded neighborhood — this brand, its indications, the channels, the applicable rules — and nothing off-scope.
  • Right resolution. Knowledge exists at several granularities: a one-line directory of what is available, a semantic summary of an entity, the full governed source. Loading everything at full resolution is both expensive and counterproductive.
  • Provably. In a regulated enterprise the agent's answer must be traceable to an approved, versioned, unaltered source. "The model probably read the right document" is not an acceptable audit posture.
  • Token budget. Context windows are finite and priced. The layer must select, not stuff.
  • Request time, at scale. Selection happens per query, per tenant, across many packs, under latency and isolation constraints.

The naïve answer — embed every document into a vector store and retrieve the top-k chunks — solves "right slice" weakly and ignores the rest. It has no concept of approval state, no provenance guarantee, no determinism, no staleness model, and no way to prove that what was served is what was evaluated. An enterprise context layer is therefore not primarily a retrieval problem; it is a supply-chain and governance problem with retrieval as one stage. That reframing drives the entire architecture below.

Load-bearing invariant
The thing the agent is served must be exactly the thing that was reviewed, evaluated, and released — byte for byte. Everything downstream (projections, indexes, caches) is disposable and rebuildable; none of it is a source of truth. This single rule is what separates an auditable context layer from a demo.

2The context supply chain

The clean way to reason about an enterprise context layer is as a supply chain that carries knowledge from a subject-matter source to an agent's working memory, with a governance spine running underneath every stage. Retrieval is one link, not the whole chain.

SME interviews, documents, tables, prior decisions — raw, untrusted
→

3Is the ontology a graph? Yes — a typed property graph with an overlay stack

This is the question most teams get wrong, so answer it precisely. In a well-formed enterprise context layer the ontology is a typed property graph: nodes are typed entities with fields; edges are typed, directional, and carry cardinality and semantic guards. It is not a flat list of records, and it is not merely a taxonomy — though a taxonomy (controlled vocabularies) and a terminology layer sit inside it. Two distinctions matter:

  • The model graph vs. the runtime projection. The authoring representation is a rich graph. The runtime representation an agent consumes is a compiled projection of that graph, flattened to the resolution the agent needs. These are different objects with different jobs; conflating them is a common error.
  • The overlay stack. Enterprise knowledge is not one graph but a precedence stack of graphs: a generic kernel, a domain base, then function / market / therapy / brand / client overlays. Higher layers override lower ones at compile time. This is how one platform serves many tenants without cloning.

How Onto_Wiz realizes it

The governed knowledge is a closed catalogue of 19 typed artifact kinds (ontowiz-spec/artifacts.py:53-77) — e.g. ENTITY_REGISTRY, TAXONOMY, JARGON_MAP, DECISION_HEURISTIC, GUARDRAIL, OVERRIDE_RULE, SOURCE_CONTRACT, EVAL_CASE. Every artifact carries governance, provenance, confidence, and an overlay layer field (base → therapy → function → client → engagement).

The graph itself is explicit. In the reference pack, entities are typed nodes and relationships are typed directed edges with cardinality and semantic guards:

# examples/.../auravia_marketing/0.1.0/ontology/marketing_ontology.yaml
entity_types:   [type.brand, type.claim, type.metric, type.join_contract, …]   # 24 typed node classes
relation_types:                                                                # typed edge schema
  - rel.measures:        {source_types:[study], target_types:[endpoint],
                          cardinality: many_to_many,
                          requires_evidence_assertion: true, causal_semantics: false}
relationships:                                                                 # concrete edges
  - {id: edge_study_endpoint, type: rel.measures, source: study_vela1, target: endpoint_easi75_week16}

In the shipped commercial pack the graph is carried inside a single entity_registry artifact — 18 connected entities (Brand, HCP, Payer, Territory, Indication, Competitor, Formulary, Channel, Signal, Forecast…) with typed edges such as treats, competes_with, distributed_via (commercial-entities.yaml:28-49). The engine is even topology-aware: a gist generator classifies nodes as hubs (≥3 inbound refs), bridges, or leaves, and can emit a GRAPH:{n}-entities,{m}-edges summary (ontowiz-ctx/.../packer/l3_generator.py:36,123-169).

Honest nuance
Today the graph lives as YAML inside artifacts and is projected to text at compile time; there is no dedicated graph database. That is correct at 24 artifacts. At enterprise scale a graph store (or graph projection) becomes a candidate component for neighborhood traversal — see §6 and §10.

The overlay stack, concretely

The manifest models the precedence stack as typed PackLayer entries. The reference pack ships a five-tier stack, each layer forbidden from broadening a correctness constraint below it:

pharma_commercial_base(10) → market_policy_us(20) → therapy_dermatology(30)
  → brand_auravia(40) → client_operating_model(50)     # higher precedence overrides lower

Source: examples/.../auravia_marketing/0.1.0/pack.yaml:29-48. The commercial pack ships layers: [] — a single implicit base — which is the correct starting point for a first vertical.

4Directory & file structure — physicalizing the layer

The context layer is physical: it is folders and files with a strict separation between hand-authored source (the product IP) and compiler-emitted projections (regenerable, never edited). This section shows both the unit (one compiled pack) and the enterprise repository shape around it.

4.1 · The compiled pack — the unit that crosses the boundary

packs/<name>/<version>/                # version is a directory level → packs are immutable per version
├── pack.yaml            # the manifest: identity, overlay layers, dependency pins,
│                        #   derived counts, eval summary, CTX pointers, IP flags
├── artifacts/           # ── AUTHORED SOURCE (the governed product) ──
│   ├── commercial-entities.yaml     #   the ontology graph (entity_registry)
│   ├── rule_safety_signal.yaml      #   a governed decision heuristic (carries delta_id)
│   └── … (one YAML per artifact id, each a typed, lifecycle-governed record)
├── context.ctx          # ── COMPILED L2 ── semantic body: one section per active artifact
├── index.l3.ctx         # ── COMPILED L3 ── <500-token directory index (goes in the system prompt)
└── pack.sig             # SHA-256 integrity seal over the payload + manifest (tamper-evident)

Confirmed on disk at packs/commercial_analytics/0.3.0/ (24 artifact YAMLs + the four derived files); canonical layout documented at ontowiz-spec/pack_manifest.py:8-12.

Authored (source of truth)

  • artifacts/*.yaml — typed ArtifactBase records; each ACTIVE state requires a governing delta_id in its lifecycle history, enforced structurally (artifacts.py:135-151).
  • In the richer reference pack, authored source is a module set: ontology/ · knowledge/ · omnichannel/ · analytics/ · agents/ · quality/ · evaluations/ · sources/.

Compiled (disposable, digest-addressed)

  • context.ctx (L2), index.l3.ctx (L3), the derived counts in pack.yaml, and pack.sig are all emitted by the compiler and never hand-edited (ontowiz-factory/compiler.py:182-192).
  • Re-running the compiler on the same source must reproduce them byte-for-byte — the determinism requirement in §8.

4.2 · The .ctx resolution layers (L0 → L3)

The context format is a bespoke, human-readable, sigil-delimited text serialization (not YAML, JSON, or a binary blob) with four resolution layers plus a manifest layer (ontowiz-ctx/core/model.py:14-19). The design principle is multi-resolution: keep the cheap directory in the prompt, fetch expensive detail on demand.

LayerHoldsResolution / costWhere it is used
L0Raw source corpus (md/yaml/json/csv)Full, unprocessedBuild-plane input only
L1Natural-language proseReadable summaryOn-demand rendering
L2 context.ctxSemantic body — one section per entity/artifact, key–value bodiesMedium; hydrated per-sectionThe pool the agent pulls from
L3 index.l3.ctxUltra-lean directory of section names + hydrate instructions<500 tokens, whole-corpusSits in the system prompt

A real L2 header and section:

§CTX v1.0 L2 DOMAIN:commercial
PACK:commercial_analytics VERSION:0.3.0
±ENTITY_REGISTRY-COMMERCIAL-ENTITIES
  BODY: entities=… relationships=type=treats; target=Indication …
±DECISION_HEURISTIC-RULE_SAFETY_SIGNAL
  …

The header magic (§CTX), sections (±NAME), and operator glyphs are defined at model.py:22-37 / parser.py:31,35; an ASCII fallback and a BPE-tokenization mode exist but are rendering options, not the storage format (serializer.py:33-44,266-300).

Design tension worth flagging
Two L3 strategies coexist: the pack compiler ships a lean instruction-style directory (hydration_protocol.py:23-84), while a richer generate_l3 that emits explicit ENTITIES / TOPOLOGY / CONSTRAINTS sections exists but is not wired into compile_pack. Converging these is a small but real decision.

5The runtime path — what the agent does, step by step

This is the core of the question: when the agent layer wants to work, what happens, and which part of context comes from which layer. The current design is whole-pack-load + deterministic governance gate + LLM-as-router hydration. Crucially, the LLM performs the actual retrieval — it reads a tiny directory and asks for exactly the sections it needs. There is (today, by deliberate choice) no vector search in this path.

  1. Authenticate, resolve tenant, pin the release. The caller arrives at the serve door with an identity; the tenant comes from the authenticated identity, never the request payload. A specific pack is pinned by name@version (target state: by content digest). No "latest" resolution at load.
    ontowiz-serve/api.py · registry.py:63-78 (traversal-guarded load)
  2. Resolve scope. The request carries query · agent_type · tags · budget. Scope narrows the candidate artifact set to what this agent, in this function, is entitled to see.
    ontowiz-runtime/context.py:194-216 (context_for_pack)
  3. Govern & gate (deterministic). Admit only servable-lifecycle artifacts, then intersect on tag keys. A gated-out artifact is never even listed downstream, so the agent cannot bypass the gate. This is the primary "right slice" filter — governance, not similarity.
    context.py:64-88 (gate)
  4. Rank (lexical, ordering only). Eligible artifacts are stable-sorted by query-term overlap so the most relevant lead the directory. This orders; it does not drop.
    context.py:91-106 (_rank_by_query)
  5. Emit the L3 directory into the system prompt. The runtime projects the L2 doc onto the gated IDs and renders a <500-token directory: "you have a knowledge base; call ctx_hydrate(section=…) to retrieve detail; only hydrate what you need." This is the only knowledge in the prompt at this point.
    context.py:116-138 → hydration_protocol.py:23-84
  6. LLM-as-router hydration — the actual retrieval. The agent reads the directory and emits ctx_hydrate(section="ENTITY-…") for exactly the sections it needs. The handler returns the L2 section body by O(1) name lookup. Multi-hop re-hydration is triggered by a low-confidence heuristic ("not found in context", …).
    hydrator.py:59-138 · benchmark.py:44-104 (HYDRATE_TOOL)
  7. Fetch governed numbers separately. Quantitative answers (metrics, NBRx vs. plan) come from a governed data tool over the warehouse — not from the knowledge sections. Knowledge context and structured data are different substrates with different trust models (§6).
    SPECIFIED — typed serving, Step 8 · structured-data fusion ROADMAP
  8. Policy gate, assemble, return with a trust receipt. A final policy gate applies; the response carries a trust envelope — pack name@version, artifacts used, mean confidence, backing Deltas, lifecycle floor — so the caller can prove what was served.
    context.py:141-155 (TrustEnvelope) · api.py:104-119

Why "LLM-as-router" instead of top-k vector search
At a corpus a <500-token directory can enumerate, letting the model name the sections it wants gives exact, explainable retrieval with zero embedding infrastructure and no statefulness (hydration_protocol.py:1-13, "the LLM IS the query router — no TF-IDF, no embeddings"). This is a sound default for bounded, governed packs. Its limit is corpus size: once a domain outgrows what one directory can list, a semantic prefilter (a vector store) becomes necessary to shortlist before routing. That transition is the main scale question in §10.
Two integrity gaps in the current path (name them)
(a) Verify-before-load is not wired in. pack.sig is written and checkable in the factory, but the serving load path never calls a verifier — the load-time verify_candidate_dir is ROADMAP (spec S1.2). (b) Always-included safety artifacts are not enforced. ALWAYS_INCLUDED_KINDS (guardrails, override rules, data quirks) is declared in the spec but the live gate never references it, so a safety artifact without a matching tag is silently dropped. Both are on the near-term backlog (card F0.10 / Step 1).

6Where each kind of context lives — files vs. database vs. graph vs. vector store

The most common architectural mistake is putting everything in one store — usually a vector database — and asking it to be the system of record. The correct design uses several substrates, each holding exactly one kind of truth, with a strict rule that projections are disposable. Here is the mapping, with Onto_Wiz's current and target realization.

SubstrateHolds (the truth it owns)Why it lives hereOnto_Wiz status
Git / pack repo
approved semantic source		 Hand-authored artifacts at an immutable commit — the governed knowledge that was approved. Reviewable, diff-able, immutable per SHA. Human approval attaches to a commit, not a mutable row. BUILT as local dirs; PackSource seam (local → Git SHA → DB-materialized) SPECIFIED
Governance / relational DB
workflow & audit truth		 Deltas, lifecycle state, approvals, reviewer identity, tenancy, idempotency, audit trail. Transactional, queryable, authenticated. This is the process record, distinct from the content record. SPECIFIED — durable GovernanceStore exists but is endpointless; three competing write models to consolidate (F0.3)
Artifact registry + object store
released truth		 Compiled, signed, attested release bundles addressed by content digest; provenance receipts; rollback pointers. Runtime loads by digest, never a Git checkout, never a glob. Immutable, verifiable, tenant-scoped. ROADMAP — target is OCI + Sigstore + SLSA; pack.sig is a precursor seal, not the end state
Ontology / graph store
structural truth		 Typed nodes + edges; neighborhoods; traversal for "what is related to X". Traversal and neighborhood queries are graph-shaped; forcing them through text or vectors loses the structure. BUILT as graph-in-YAML + L2/L3 projection; a dedicated graph store is a scale option, not present
Vector store
semantic shortlist		 Embeddings of sections/chunks for approximate similarity — a prefilter, never the source. Needed when the corpus outgrows a directory the model can route over, or for cross-pack discovery. ROADMAP — deliberately absent today; "semantic search when a vector store is added" is a named future (evidence.py:369-371)
Cache / projections
disposable		 Compiled .ctx layers, lexical index, embeddings, per-tenant materializations. Rebuildable from source at any time. Fast to read, safe to drop. Never a source of truth. BUILT — L2/L3 are exactly this; the invariant "projections are disposable" is committed
The rule that ties the substrates together
Each substrate owns one truth: Git owns approved source, the relational DB owns workflow, the registry owns released bytes, the graph owns structure, the vector store owns a similarity shortlist, the cache owns nothing. The compiled, attested bundle in the registry is the single served artifact; everything else either feeds it (source, workflow) or is derived from it (projections). "The served thing IS the eval-gated thing" — serve-time multi-pack merging is rejected; overlays are resolved to one sealed pack at compile time.

So — vector store or not?

For a bounded, governed pack the honest answer is you may not need one, and starting without it is defensible. Onto_Wiz's LLM-as-router works because a governed pack is small and its directory fits the prompt. A vector store earns its place at three specific thresholds: (1) a single domain's active sections exceed what a <500-token directory can enumerate; (2) you need cross-pack discovery ("which of 200 packs is relevant to this query"); or (3) you ingest large unstructured corpora where governance happens after retrieval rather than before. Until one of those is real, a vector store adds operational cost and a second, weaker provenance path. The architecture should reserve the seam (a retrieval interface) without building the store prematurely — which is exactly the posture of the PackSource/projection design.

8Evaluation & trust — proving the layer works

An enterprise context layer must prove two things: that a pack loads and verifies, and that it changes agent behavior for the better. Onto_Wiz measures the second directly with an agent-lift benchmark: the same question is answered twice — once with the pack wired in through the real router loop, once blind — and the mean delta is the lift.

  • Same code path as production. The with-pack answer uses the exact context_for_pack + hydrate loop the product ships, so the benchmark measures the real system, not a proxy (ontowiz-factory/benchmark.py).
  • A gate, not a vanity metric. Promotion is blocked unless pass_rate ≥ min and lift ≥ min_lift — "a pack that passes its evals but adds no agent lift is blocked" (evals.py:94-107). The shipped commercial pack shows +0.308 measured lift (v0.1.0, term-adoption).
  • The verdict binds to the content. The eval receipt is (target state) keyed to the candidate_digest, so you cannot serve one pack and cite another's evaluation. Today the summary is baked into pack.yaml as PackEvalSummary; making it an immutable digest-bound receipt is S1.3 (SPECIFIED).
The property this buys
At serve time the answer carries a trust envelope; at release time the pack carries an eval receipt bound to its digest. Together they close the loop the naïve RAG stack cannot: you can prove, after the fact, that what the agent used was approved, unaltered, and measured to help.

9Governance as a control system

Everything above rests on a governance spine that most "context layer" designs omit. The non-negotiable invariants (from DOMAIN_PACK_PLATFORM_BUILD_INSTRUCTION_SET_2026-07.md §3) are worth stating because they are what make the architecture enterprise-grade rather than a clever cache:

  • LLM output is a candidate, never an authority. Extraction proposes; a human Delta review approves. No model output reaches a release decision unreviewed.
  • Delta-gated promotion. An artifact cannot become ACTIVE without a governing delta_id — enforced in the type system, not by convention (artifacts.py:135-151). This is the platform's single strongest built idea.
  • Deterministic, network-free compile. Same source → byte-identical output, regardless of input order, working directory, or wall-clock. This is what S1.1 (in review now) locks down: an explicit input/output inventory and a reproducible candidate_digest.
  • Candidate bytes never change after the digest is computed. No volatile value (timestamp, path, eval result) is ever written inside a candidate directory.
  • Aggregate scores cannot hide a critical failure. A compliance, privacy, tenancy, or numeric failure is not averaged away by a good overall score.
  • Synthetic content is permanently barred from production release, and the kernel may not hard-code any one client or domain — enforced by the "second-consumer gate" (§10).
  • Typed staleness, not a "last updated" badge. Staleness has eight/nine typed reasons (source expired, label changed, review overdue, dependent changed, eval too old, projection obsolete…), each carrying an owner and a required remediation. This is ROADMAP — today freshness fields are echoed to the UI as if measured.

Governance also needs organizational shape: separation of duties (the build plane "cannot approve its own output"), authenticated principals on every mutation, and contribution scores that "never grant medical, legal, regulatory, or MLR authority." The write-model consolidation onto a single system of record is the live F0.3 decision.

10Scale & multi-tenancy

Scaling a context layer to an enterprise is scale by composition, not by cloning. A new domain or client should register overlays, validators, and profiles — not fork the engine.

  • Compile-time overlay resolution. The overlay stack is resolved into one digest-addressed, sealed pack at compile time; the runtime always serves exactly one pack per agent. Serve-time multi-pack merging is rejected — this preserves "the served thing IS the eval-gated thing."
  • The second-consumer gate (Step 10). The platform is only proven domain-independent when a second, non-brand pack compiles and serves "without a schema fork, copied base ontology, new compiler, new lifecycle, or new serving path." This is the structural guard against the kernel quietly hard-coding the first client.
  • Tenant isolation is total. Every row, object, cache entry, vector namespace, and projection carries tenant + candidate/release scope; the first pharma deployment isolates database, object storage, registry namespace, projections, keys, backups, logs, and runtime identity into a client-isolated VPC.
Honest scale limits (from the platform's own audit)
The system is proven at ~24 artifacts and unquantified beyond that: the L3 directory grows linearly with active sections, identifier extraction is O(n²), and retrieval is lexical-only. A dedicated "scale probe" (M2) is planned to assign real numbers. Multi-tenant confidential segregation "has no mechanism" yet — the direction (client overlays in separate repos, per-tenant registries) is right but undemonstrated. These are the thresholds at which a vector store, a graph store, and hardened tenancy stop being optional.

12Recommended target architecture & sequence

Pulling it together: the target is three deployable planes over the shared substrate set, built back-to-front so the integrity kernel is locked before the surfaces that depend on it.

Control plane (Tier A, key-free of model creds) — catalog · governance · curation · eval metadata · releases · admin. Cannot hold model credentials or serve agent traffic.
Build plane (Tier B)
Isolated compiler/eval workers. Hold model creds + source access. Cannot activate or approve their own output.
→
Registry (digest-addressed)
Signed, attested release bundles. The only thing the runtime loads.
→
Data plane (Tier A, per-tenant)
Projections · context resolution · agent traffic. Cannot mutate governance or serve an unattested candidate.
Substrates: Git (approved source) · relational DB (workflow/audit) · registry+object store (released bytes) · graph (structure, at scale) · vector (shortlist, at scale) · cache (disposable projections). Boundary rule: Tier A → Tier A only; Tier A → Tier B is a build failure (tools/check_boundaries.py).
Figure 3 — Target topology (ADR-019). One monorepo, three independently deployable planes, over substrates that each own one truth. Built as a client-isolated VPC for the first pharma deployment.

Build sequence (backend-first, and where we are)

  1. Integrity kernel — deterministic compile + inventory (S1.1, in review now) → verify-before-load + always-included enforcement (S1.2) → digest-bound eval receipt (S1.3).
  2. Schema kernel (Step 2) — freeze the canonical contracts + registry + the PackSource/ArtifactRegistry seams. Everything downstream writes against stable interfaces.
  3. Source → candidate lineage + consolidation (Steps 3–5, M3/M4) — the produce side and the resolver; this is where the single biggest gap (consolidation) must get an owner.
  4. Projections & typed serving (Step 8) — including the structured-data path for the analytics half of the vertical examples; add graph/vector projections only at the scale thresholds in §10.
  5. First executable exam (Steps 6–7) — MLR + brand-analytics verticals against the reference pack, production release still barred.
  6. Control plane, one screen at a time — replace the synthetic fixtures with real authoring/eval/release/simulator surfaces once the backend they depend on exists.
The one principle to keep
Build the governance and integrity spine before the retrieval sophistication. A vector store bolted onto an ungoverned corpus is a faster way to serve unapproved content; the same vector store over a governed, gated, attested pack is a genuine scale improvement. Sequence protects the difference.

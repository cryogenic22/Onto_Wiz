Validated operating blueprint

One semantic core. Three executable workload views. Evidence at every boundary.

A domain pack is a governed, versioned context product that binds meaning, evidence, policy, data semantics, agent operations and evaluations into a reproducible release. MLR, market-research mining and brand analytics should share the same product, market, audience, source and governance identities while receiving different task-specific context views.

How to use this document

This is the team-facing architecture baseline. The readiness audit remains an evidence snapshot; the earlier strategy remains conceptual detail.

Validated here means repository claims were cross-checked. It is not clinical, regulatory or client-data validation.

01

Executive verdict

The system has a credible governed consume path and a strong target fixture, but it does not yet deliver these workloads end to end.

Product decision

One core, many views

Do not create independent MLR, MR and analytics knowledge bases. Compile thin workload releases from shared governed modules and overlays.

Engineering decision

Back end before workflow UI

Make candidate integrity, schema, lineage, evaluation and typed serving executable before connecting the control-plane screens.

Authority decision

Design is not capability

Auravia is a coherent non-production exam. It is not compiler-compatible or served by the current runtime.

Scale decision

Compile-time resolution

Resolve base modules and private overlays into one evaluated release. Runtime serves the released composition, not an untested merge.

Practical implication: the shortest path is not another broad ontology. It is one generic release spine plus three narrow vertical slices that prove evidence-critical, unstructured-research and structured-analytics behavior.

03

The domain-pack product model

Modules describe capabilities; layers describe precedence and applicability; releases bind the exact composition evaluated for a named workload.

Shared semantic core

Identity and meaning once

Brand, product, indication, market, audience, segment, metric, source, policy and evidence identities are reused across functions.

Capability modules

Typed knowledge facets

Claims/MLR, market research, analytics, forecasting, segmentation and planning add contracts without duplicating the shared core.

Workload release

Minimum eligible context

A pinned, digest-addressed composition exposes only the operations and artifacts required by one agent decision.

Layer 1Generic kernel

Identity, evidence, applicability, lifecycle, provenance and trust.

Layer 2Pharma commercial base

Product, market, stakeholder, engagement, dataset and decision concepts.

Layer 3Function module

MLR, research or analytics contracts and evaluations.

Layer 4Market / policy

Jurisdiction, audience, purpose, channel and permission constraints.

Layer 5Therapy / brand / client

Evidence, local terminology, data mappings and operating rules.

ReleaseAgent context view

Exact pins, operations, receipts, expiry and rollback target.

Non-negotiable: a higher layer may narrow safety, privacy, regulatory or access permissions. It cannot silently broaden them. Every override is explicit, typed, reviewed and regression-tested.
04

Architecture and storage placement

The context layer is a compiled product across five representations; it is not one database and agents never call storage directly.

1. Authority plane
Original documents, recordings, labels, policies, approved assets and business data remain in authoritative client systems. OntoWiz records immutable identities, hashes, access class, versions and locators.
DMS / object store / MLR system / warehouse
2. Semantic source plane
Human-readable typed YAML/JSON for concepts, claims, evidence links, metrics, joins, policies, research insights, decisions, agent contracts and golden cases.
Domain-pack Git repositories
3. Build and governance plane
Sources, exact spans and candidates become reviewed Deltas; the resolver pins dependencies, rejects conflicts and creates deterministic candidates plus external receipts.
OntoWiz control data + build workers
4. Projection plane
A released semantic source produces graph edges, lexical/vector retrieval, catalog records and typed runtime bundles. All projections carry release and artifact identity and are disposable.
Graph / OpenSearch / vector index / registry
5. Data-product plane
Operational rows and measures stay in governed data products. The pack contains table, column, metric, join, grain, quality and access contracts used by a typed query service.
Warehouse / lakehouse / semantic query API
6. Agent serving plane
Agents call typed operations. Each response returns resolved scope, artifacts, evidence or query receipts, policy versions, freshness, confidence, release identity and abstention state.
REST / MCP / SDK behind tenant policy

Context evolution and governance

Every change follows the same lineage chain whether it begins in a document, a transcript, an SME conversation, a data incident or an agent correction.

TriggerImmutable observation

New source, changed policy, SME assertion, failed evaluation or usage correction.

DiscoverCandidate + exact span

Typed extraction with source identity, locator, confidence and scope; never direct release mutation.

ReconcileDedup + conflict

Compare semantic identity, support, contradictions, applicability and layer precedence.

GovernDelta decision

Authenticated owner approves, rejects, supersedes or requests evidence with reason.

ProveCompile + evaluate

Deterministic candidate, impact-selected suites, critical gates and external receipts.

ReleaseAttest + monitor

Named channel, consumer pins, rollback, staleness, telemetry and feedback linkage.

06

How any agent consumes the layer

The ontology routes; deterministic facts and rules are compiled; semantic material is retrieved; business rows are queried through governed tools.

Correctness critical

Compile deterministically

Definitions, eligibility, claims, risk, formulas, grains, joins, policy and prohibitions are never similarity-selected.

Relevance

Retrieve with filters

Research reports, transcripts, approved plans and evidence passages use metadata eligibility before semantic ranking.

Numbers

Query data products

The agent receives schema and typed operations, not warehouse rows or arbitrary SQL in its prompt.

Decision support

Traverse evidence

Facts, hypotheses, conflicts, policy, approvals and outcomes remain distinguishable in the response.

Common response envelope: tenant + pack/release + resolved scope + artifact versions + evidence spans or query receipts + policy/label versions + freshness and quality + human-approval requirement + explicit BLOCK, ROUTE, ABSTAIN or eligible result.

Vertical 1 · Evidence and policy critical

MLR assistance and promotional-content preflight

Accelerate evidence assembly and first-pass review quality without representing automated approval or replacing the authorized MLR workflow.

First target decisionMay this scoped draft proceed to human review, what must change, and what exact evidence and policy govern each finding?
Business outcome
Fewer avoidable review cycles, higher first-pass quality, faster reuse of approved propositions, and complete traceability to current source and policy.
Decision families
Claim eligibility; semantic equivalence; evidence sufficiency; qualifier/comparator/timepoint preservation; risk coupling; audience, market, purpose and channel applicability; route/block/abstain.
Agent operations
get_content_brief · get_eligible_claims · explain_claim_support · get_required_risk · validate_draft · explain_finding
Semantic chain
Product → indication/population → semantic claim → permitted variant → support assertion → exact evidence span → limitations → risk bundle → market/audience/channel policy → draft finding → human review decision.
Authoritative inputs
Current label/PI, study and evidence references, approved claim library, market policy, risk statements, approved asset metadata and prior ratified review decisions. Raw authority stays outside the pack.
Non-compensable gates
Off-label implication, unsupported comparative/superiority claim, safety minimization, missing required risk, wrong scope, inaccessible evidence, expired label or any automated approval language.
Ontology deliverable

Brand, ingredient, indication, population, endpoint, study, claim, evidence, risk, audience, purpose, channel, policy, asset and finding relationships.

Knowledge deliverable

Claim dossiers, support assertions, variants, mandatory statements, prohibited transformations, risk bundles, MLR rules and decision exemplars.

Agent deliverable

Typed operations, input scope, structured finding schema, trust envelope, abstention states and human-review boundary.

Quality deliverable

Positive, negative and adversarial cases for qualifiers, equivalence, risk, market, audience, off-label and approval representation.

Generic platformSource, evidence and applicability contracts

Registry, exact spans, lifecycle, Delta, deterministic compile, receipts and typed refusal.

Function moduleClaims and MLR schema

ClaimDossier, SupportAssertion, RiskBundle, MLRPolicy, DraftFinding and operation renderers.

Client integrationAuthority adapters

DMS/label library, approved-claim system, asset metadata and MLR workflow deep links.

Human rolesEvidence curator + MLR authority

Curator proposes and traces; authorized reviewers decide. Contribution score never grants authority.

First executable slice and definition of done

Compile a synthetic US HCP slice from the Auravia target fixture: 5–8 scoped claims, support spans, at least two risk bundles, one current label, one market policy and one channel policy.

  • Runtime serves all six named operations from one released view.
  • At least 20 can-fail cases include semantic broadening and wrong-market traps.
  • Every finding resolves to governing artifacts and exact evidence.
  • No output path can emit MLR approval or hide human review.
  • Candidate is deterministic, verified before load and externally receipted.
  • Control plane renders real findings and lineage, not mock outcomes.

Vertical 2 · Unstructured evidence and synthesis

Market-research mining and insight ratification

Convert briefs, reports, interviews, transcripts and discussions into traceable, method-qualified insights without fabricating quotes or generalizing beyond the sample.

First target decisionWhat did the researched audience say and mean, where do views differ, how strong is the evidence, and what remains unresolved?
Business outcome
Faster evidence review, reusable insight memory across studies, explicit contradictions and limitations, and less loss of respondent and methodology context.
Decision families
Question coverage; code/theme validity; cohort differences; saturation; contradiction; evidence strength; implication versus hypothesis; triangulation with structured signals; escalation for SME ratification.
Agent operations
search_research · get_theme · trace_insight · compare_cohorts · get_contradictions · triangulate_signal · propose_candidate
Semantic chain
Research question → study design → sample/cohort → discussion-guide item → transcript turn → exact verbatim → code → theme → insight → limitation/contradiction → implication or hypothesis → ratified candidate.
Authoritative inputs
Approved brief, methodology, sample frame, guide, transcripts/audio, moderator notes, coded output and final report. Structured trackers may triangulate but never overwrite qualitative provenance.
Non-compensable gates
Fabricated or altered quote, lost respondent/source, confidentiality leak, sample overreach, missing methodology, conflated cohorts, unsupported prevalence language or hidden contradictory evidence.
Ontology deliverable

Study, research question, method, sample frame, cohort, respondent class, guide question, transcript span, code, theme, insight, contradiction and limitation.

Knowledge deliverable

Evidence-linked themes, codebook, jargon map, cohort comparisons, insight dossiers, unresolved questions and ratified decision heuristics.

Retrieval deliverable

Chunk and span index with study, question, cohort, speaker, date, authority and access metadata; semantic rank only after eligibility filters.

Quality deliverable

Quote fidelity, attribution, study boundary, contradiction, duplicate theme, confidentiality, saturation and overgeneralization tests.

Generic platformImmutable source and candidate lineage

Parser boundary, source hashes, exact spans, runs, candidates, reconciliation and durable Delta workflow.

Function moduleResearch evidence schema

StudyDesign, SampleFrame, Verbatim, Code, Theme, Insight, Limitation and Contradiction contracts.

Client integrationDocument and transcript adapters

DMS/object store, transcription identity, consent/access metadata and optional tracker query service.

Human rolesResearch lead + domain SME

Research lead validates method and interpretation; SME ratifies domain meaning and operational implications.

First executable slice and definition of done

Use a synthetic study with one brief, one guide, 20 short interviews, two cohorts and known contradictory views. The existing legacy parser stack may be ported behind the new source boundary; the current ontology/domains/research.yaml is R&D research and must not be reused as market-research semantics.

  • Every insight resolves through themes and exact verbatim spans.
  • Cohort comparisons preserve sample and methodology limitations.
  • Dedup and contradiction pass surfaces candidate pairs for review.
  • Semantic search applies tenant, study and access filters first.
  • At least 30 cases cover quote, attribution and overreach failures.
  • SME ratification creates governed Deltas, never direct pack edits.

Vertical 3 · Structured semantics and diagnostic reasoning

Brand analytics and performance diagnosis

Give agents reproducible metric meaning, safe query paths and evidence-limited diagnosis while keeping business rows in governed data products.

First target decisionWhere is the brand off plan, what arithmetic and evidence support the variance, what are plausible drivers, and what cannot be claimed causally?
Business outcome
Consistent KPI answers, fewer metric-definition disputes, faster root-cause triage, reproducible numbers and explicit separation of observed facts from hypotheses.
Decision families
Actual versus plan; trend and benchmark; geography/cohort decomposition; access, demand, execution and engagement hypotheses; data-quality eligibility; causal versus descriptive interpretation; next analysis.
Agent operations
get_kpi_tree · get_metric_definition · get_join_path · query_metric · compare_metric · decompose_variance · diagnose_brand_variance · trace_metric_lineage
Semantic chain
Business question → KPI tree → metric/version → formula/unit/grain → dimensions/filters → table/column → approved join → source snapshot → quality checks → query receipt → observation → hypothesis → evidence/confounder → next action.
Authoritative inputs
Metric catalogue, plan versions, warehouse/lakehouse catalog, table and column definitions, join keys, refresh and revision policy, data-quality results, privacy/suppression policy and experiment registry.
Non-compensable gates
Wrong formula, denominator, unit, grain or period; fan-out/double count; stale or incomplete snapshot; undeclared join; privacy breach; plan-version mix; or causal claim without eligible causal evidence.
Ontology deliverable

Brand, market, geography, channel, segment, KPI, metric, dimension, dataset, table, column, join, snapshot, plan, observation, hypothesis and experiment.

Semantic-layer deliverable

Metric contracts, KPI edges, formulas, grains, allowable dimensions, table/column mappings, governed joins, quality and interpretation rules.

Runtime deliverable

Typed query plans and receipts, no arbitrary SQL, no raw rows in prompts, deterministic comparisons and fact/hypothesis/causal-status separation.

Quality deliverable

Executable fixtures for formulas, joins, temporal boundaries, missingness, revisions, suppression, decomposition and causal restraint.

Generic platformSchema registry and receipts

Metric/table/join/source contracts, release pins, access decisions, query receipts and workload evaluations.

Function moduleAnalytics reasoning schema

KPI tree, comparison, decomposition, observation, hypothesis, confounder, experiment and permitted action.

Client integrationTyped query adapter

Warehouse semantic service, catalog metadata, plan snapshots, DQ service and experiment registry.

Human rolesMetric owner + data steward + brand SME

Metric owner governs meaning; steward governs data; SME validates interpretation and decision utility.

First executable slice and definition of done

Make the synthetic Auravia Northeast NBRx versus plan question executable with NBRx, active writers, writer depth, PA rejection and email proxy metrics, declared snapshots and approved join paths.

  • All displayed numbers recompute from typed query fixtures.
  • Metric, grain, period, plan and source versions appear in receipts.
  • Undeclared joins and row-level prompt retrieval are rejected.
  • Diagnosis separates facts, hypotheses, contradictions and confounders.
  • Email correlation cannot be presented as incremental causality.
  • Latest release passes numeric, DQ, privacy and restraint gates.

The three examples share most of the platform. Build common integrity and governance once, then add function-specific schemas and evaluations.

Shared trust spine

3. Freeze the semantic kernel and registry

Add source/evidence, applicability, relationship, claim/risk/policy, research-evidence, metric/table/join, agent-operation, evaluation and release contracts with migrations.

No domain hard-coding

4. Build source-to-candidate lineage and consolidation

Port suitable parser components behind the model-free boundary; persist runs, spans and candidates; add dedup, contradiction and layer-conflict findings; route through one governance write model.

Capture and curation spine

5. Add projection and typed-serving adapters

Generate registry, graph, OpenSearch/vector and runtime bundles from one release. Add typed evidence search and semantic-query operations with tenant and policy enforcement.

Agents call contracts

6. Deliver MLR and analytics as the first executable exam

They prove both correctness-critical evidence and structured numeric behavior. Market research follows on the same lineage spine and adds the unstructured consolidation stress test.

Vertical acceptance

7. Connect the control plane to real workflow state

Replace one mocked screen at a time only when its backend slice exists: source/candidate workbench, governance queue, eval center, release center, simulator and feedback.

UI follows executable contracts

How the ontology is organized

Not one giant ontology — a meta-model instantiated by 11 domain ontologies, sliced into layered, governed packs. This is what prevents the classic failure: everyone re-discovering "payer policy" and "pull-through" in slightly different ways.

① Meta-model (the schema)

A small, stable vocabulary every domain reuses: EntityType, RelationshipType, Metric, Signal, EvidenceItem. Defining it once is what makes domains interoperable.

② Domain ontologies (11)

Each domain instantiates the meta-model with its own entities, metrics, signals and inference rules. They connect through cross-domain edges (the Value Stream tab).

③ Layered packs (the product)

A shippable pack is a governed slice of the graph, stacked by precedence so client/engagement specifics override the base without forking it.

Domain & graph strategy — how we build it

The ontology is a property graph: typed nodes, typed edges, every edge carrying confidence, provenance and a governed lifecycle. Here is the node/edge taxonomy and how edges get created.

Node types (what becomes a node)

  • Entity — Brand, HCP, Payer, Territory… (real-world things)
  • Metric — TRx, NBRx, market share, PA rate
  • Signal — an observed change ("volume down 8%")
  • Observation / Evidence — the data point + its source
  • Hypothesis — a candidate driver of a signal
  • Constraint (Guardrail) — what NOT to conclude
  • Action — recommended cross-functional move
  • Pattern — a reusable judgement abstraction

Edge types (how nodes connect)

  • Structural — treats, competes_with, covered_by (the entity model)
  • LEADS_TO — Signal → Hypothesis → Action
  • SUPPORTS / CONTRADICTS — Evidence → Hypothesis
  • REQUIRES_EVIDENCE — Hypothesis → Evidence needed
  • BLOCKED_BY — Action → Constraint
  • HAS_SOURCE — Signal → contributing Entity
  • every edge: confidence · provenance · lifecycle

How edges are created — four sources, one governance gate

SEED ontology YAML (entities, relationships, 19 rules) ──┐ MINE decks / code / SQL / transcripts → candidate edges ──┤ ELICIT Domain Forge — SME confirms/ranks/repairs/dissents ──┼──► DELTA ──► governed graph REASON agent run-time: new Signal→Hypothesis→Action edges ──┘ (proposed → reviewed → active) nothing reaches the live graph by direct write — every edge is the effect of a merged Delta

Confidence

Each node/edge carries [0–1] confidence + reliability (HARD / SOFT / RUMOR). Low-confidence, high-impact edges become Forge missions.

Provenance

Every edge points back to its source (slide, code line, SME, eval). "Searchable rubbish is still rubbish" — provenance is what makes it trustworthy.

Lifecycle

candidate → proposed → reviewed → active → evaluated → superseded. Decks never jump straight to active.

A pack = a governed subgraph

Compiling commercial_analytics walks the active commercial subgraph, serializes it into a CTX context layer + manifest. The agent hydrates only the slice a query needs — governance gate first, so a draft edge is never even offered.

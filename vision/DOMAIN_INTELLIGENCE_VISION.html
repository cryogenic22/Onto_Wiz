The Domain Intelligence Factory

A modular, governed knowledge capability — built in Onto_Wiz, powered by SpecOmagic's extraction engine, run on market_zero's loop harness, packaged with aura.ai's domain-pack pattern — consumable by any agent we ever build.
Vision & Approach v1 — for brainstorm 10 June 2026 Source: spec_raw.md + 4-repo deep scan
The one-sentence thesis: Stop building knowledge into agents; build a governed domain layer that agents subscribe to. Extract candidates from artifacts → elicit judgement through Domain Forge → govern through Deltas → compile into versioned Domain Packs → test through evals → consume through a one-call SDK → improve through closed loops. The packs are the product. Everything else is the factory.

My core finding from scanning all four repos: we are not starting a build — we are doing an assembly. Roughly 70% of the spec already exists in production-grade form, just scattered across four codebases that each solved a different slice of the same problem. The work is to define the seams, pick the dependency directions, and wire the loops. That changes the plan from "6 months of greenfield" to "weeks of integration plus targeted new builds."

What "modular knowledge capability" means concretely

  • One import for any agent: from onto_wiz import get_context — pass a query, pack id, token budget; get back a governed, provenance-tagged, lifecycle-gated context package. SpecOmagic's SDK already has this shape; we put governance and packs behind it.
  • Packs are versioned, compiled objects — not folders of YAML. Compile = validate schema + resolve overlay stack + run eval gate + stamp version + emit manifest. An agent pins commercial_analytics@1.3 the way it pins a pip dependency.
  • Every mutation is a Delta. Extraction proposes, Forge validates, curator approves, compiler ships. Nothing jumps from a midnight PPT slide to production context.
  • Every artifact has a testable consequence. Adding a DataQuirk must block a known-wrong answer; adding a heuristic must change agent behaviour in a measurable eval. No eval case, no promotion.

The unified artifact model (merge, don't duplicate)

  • From SpecOmagic (keep as-is): InstructionSet, JargonMap, EntityRegistry, Taxonomy, OverrideRule, FewShotLibrary, PromptTemplate, DecisionHeuristic, DataQuirk, ProcessPlaybook
  • From Onto_Wiz (keep as-is): JudgmentPattern, Guardrail, ActionTemplate, EvidenceItem, GraphNode/Edge
  • New per spec (small builds): EvalCase (first-class!), QuestionPlaybook, MetricDefinition, SourceContract, AntiPattern, ExceptionRule
  • The bridge: one thin adapter making SpecOmagic's lifecycle (DRAFT→REVIEW→VERIFIED→ACTIVE) transitions occur only via Onto_Wiz Deltas. The blueprint already maps DecisionHeuristic→JudgmentPattern, DataQuirk→Guardrail+OverrideRule, ProcessPlaybook→ActionTemplate.

03 The five loops — market_zero's harness, repurposed for knowledge

market_zero's deepest pattern is not any single service — it's the steward discipline: collect ranked signals → look up a deterministic action → execute → measure the quality delta → commit or revert → write the audit row. We port that discipline to knowledge curation. Five loops, each one a thin adaptation of code that already runs in production:

scheduled / on-upload

Loop 1 — Mining loop (sources → candidates)

ingest docs/code → SpecOmagic HYBRID extract → dedupe/cluster → candidate artifacts as PROPOSED Deltas Port: scheduler/runner.py pattern (idempotent phases, since-cursors, DLQ) wrapping SpecOmagic's ExtractionPipeline.extract_and_save(). New build: code/SQL rule miner ("institutional judgement wearing a hoodie") + duplicate clustering.
daily, autonomous

Loop 2 — Knowledge Steward loop (signals → curation actions & missions)

collect signals (staleness, conflicts, low confidence, missing evals, duplicate clusters) → rank by impact → deterministic action OR generate a Forge mission → measure pack-quality delta → commit/revert → audit Port: services/data_steward.py nearly verbatim — swap FAIR score for a Pack Quality Score (coverage × eval coverage × freshness × confidence). This is the loop that turns the game from a quiz into a targeted curation accelerator: weak spots become missions automatically.
5-min daily / weekly / multiplayer

Loop 3 — Forge elicitation loop (SME judgement → deltas + evals)

steward queues high-impact cards → SME plays mission (validate / rank / spot-the-bad-insight / same-or-different / name-the-caveat) → every round emits: pack delta + gold eval label + confidence update Build on: Onto_Wiz Situation Room UI + delta_generator.py (game session → Delta already works) + SpecOmagic InterviewAgent for deep-dive sessions. Score quality & useful dissent, never volume.
on every pack compile (CI gate)

Loop 4 — Eval loop (pack change → proof of lift)

pack delta merged → BatchEval runs EvalCase suite → agent-lift benchmark (with pack vs without) → thresholds pass → version stamped & promoted; fail → blocked + steward signal Port: aura.ai quality-gate/run_evals.py + .quality-gate.json thresholds pattern + SpecOmagic eval/ (rubrics, LLMJudge, BatchEval). EvalCase becomes a first-class artifact so Forge rounds literally manufacture the test suite.
continuous

Loop 5 — Consumption feedback loop (agent usage → better packs)

agents call get_context() → telemetry (which artifacts used, hit/miss, confidence, corrections) → failed retrievals propose aliases, low-confidence answers flag artifacts, corrections become PROPOSED Deltas + new EvalCases Port: services/feedback_loops.py three-loop template (pattern→weight, failure→ontology, quality→flag) + learning_service.py EWMA for per-artifact reliability. One correction should prevent a whole class of future errors — that's the "correction reuse" metric.

Plus the meta-loop: drop market_zero's harness/generate.py + measure.py into Onto_Wiz itself so the development of this system runs with anti-slop catalogs, test ratchets and weekly health reports. The factory gets a factory.

05 Key decisions to brainstorm

D1 — How do we consume SpecOmagic: pip dependency, git submodule, or vendor the code in?

It's already packaged (pip install specomagic). Vendoring gives freedom to fuse models but forks the 70-test-file codebase; depending keeps one source of truth but means cross-repo PRs when the artifact model needs to evolve.

Depend on it as a library (editable install during dev: pip install -e ../SpecOmagic). Onto_Wiz adds governance, packs and loops around it. Only fuse if the bridge gets painful.

D2 — Persistence: ADR-005 says in-memory, but packs and deltas must survive restarts.

SpecOmagic already persists to YAML; market_zero is Postgres+pgvector; Onto_Wiz core stores are in-memory by deliberate ADR.

Two-tier: packs + artifacts stay YAML/file-backed (git-versionable, diffable, reviewable — knowledge as code), while Deltas/telemetry/eval-runs go to SQLite now, Postgres when multi-user. Supersede ADR-005 with a new ADR.

D3 — Two governance models exist: SpecOmagic lifecycle states vs Onto_Wiz Deltas. Who wins?

SpecOmagic: DRAFT→REVIEW→VERIFIED→ACTIVE on the artifact. Onto_Wiz: every change is a Delta with blast radius + HITL routing + audit.

Deltas win — they're the spec's "govern through deltas" mantra. Artifact lifecycle states remain, but transitions are effects of merged Deltas. The bridge adapter is ~one file.

D4 — First proof scope: confirm the spec's pick?

Spec says: Commercial Analytics Base Pack — brand performance diagnosis, flagship question "Why did Brand X lose share this quarter?", benchmarked with-pack vs without-pack. Onto_Wiz already has ontology/commercial.yaml (TRx, NBRx, market_share, PA_rate, signals, rules) + synthetic Compellium dataset + scenarios — a real head start.

Yes — and use MarketZero as the first consuming agent for the benchmark, which also proves the cross-repo consumption story.

D5 — Where does the graph fit in packs?

Packs are artifact bundles; the concept graph (relationships, supports/contradicts) lives in GraphStore. Does a compiled pack embed its subgraph, or reference the central graph?

Embed a serialized subgraph snapshot per pack version (portable, pinnable), keep the live graph central for curation. Decide in Phase 2 — reversible.

07 Risks I'd watch (spec's five, plus two from the code scan)

  • Game as decoration — every Forge round MUST emit a delta + eval, or it's theatre. Enforced in the round schema itself, not by convention.
  • Over-extraction — extractors propose, never promote. Already structurally true once the Delta bridge exists.
  • One giant ontology — layered packs only; the LayeredStore merge rules already encode this.
  • Points for speed — score consensus-correctness, novelty, impact, useful dissent. Never volume.
  • Two artifact models drifting (new) — if the bridge isn't built in Phase 1, SpecOmagic and Onto_Wiz models will diverge and we'll re-merge painfully later. Do D3 first.
  • Integration sprawl (new) — four repos, four idioms. The harness + ADR-007 boundary checks + anti-slop catalog are the antidote; that's why Phase 0 is the harness.
  • Elicitation ≠ Q&A — Forge stays its own surface, never merged into analyst chat.
Bottom line: the spec asks for a five-layer domain intelligence factory. The scan shows layer 1 (mining) is SpecOmagic, layer 2 (objects) is SpecOmagic+Onto_Wiz merged via one bridge, layer 3 (compiler) is aura.ai's pattern + SpecOmagic's LayeredStore, layer 4 (Forge) is the Situation Room grown into missions, layer 5 (evals/feedback) is market_zero's steward + feedback loops ported. First proof: Commercial Analytics Base Pack answering "Why did Brand X lose share?" with measured agent lift. If that number moves, we have a product, not a demo.

Foundations & The Move

How we consolidate four codebases into one governed monorepo, split it into shippable vs. secret-sauce tiers, wire CTX as the context engine, and expose everything headless through library + REST + MCP — so any agent, ours or a client's, gets the right domain knowledge on every query without ever seeing how it was made.
Foundation Design v110 June 2026supersedes nothing — extends the Vision doc
The governing idea: one monorepo, two tiers. Tier A (the SDK) is what a client ever touches — contracts, the CTX context engine, the runtime, and the headless server. Tier B (the factory) is the secret sauce — governance, mining, the Forge, the loops, the compiler — and it never leaves our infrastructure. The product that crosses the boundary is neither code nor source: it's a compiled, signed, license-gated Domain Pack. The compiler runs in Tier B; the runtime in Tier A only consumes its output.

01 Package topology — six packages, one boundary that matters

Everything lands under Onto_Wiz/packages/ as independently-buildable wheels sharing the ontowiz_* prefix. The single load-bearing rule, enforced in CI exactly like your existing ADR-007 boundary check: Tier A must never import Tier B. Break that, and the secret sauce leaks into a client wheel.

SHIPS TO CLIENTS · TIER A · "the SDK"
  • ontowiz-spec — pure data contracts: the unified artifact model, pack manifest schema, CTX types. Zero logic, safe to ship. Everything depends on this; it depends on nothing.
  • ontowiz-ctx — the CTX engine (vendored from CTX.ai): parser, serializer, validator, hydrator, packer, guard. Zero runtime deps. This is the context-management engine.
  • ontowiz-runtime — pack loading + LayeredStore + the context assembler + get_context(). What a consumer agent imports directly. Reads compiled packs; contains no extraction or governance logic.
  • ontowiz-serve — the headless layer: FastAPI REST + MCP server. Thin adapters over runtime. Shippable as a container.
INTERNAL ONLY · TIER B · "the factory"
  • ontowiz-core — the governance brain: Delta model, blast radius, HITL routing, JudgmentPattern/Guardrail, Evidence, GraphStore, SemanticStore. (Onto_Wiz src/core today.)
  • ontowiz-factory — the secret sauce, as submodules:
    · mining/ — SpecOmagic's 9 extractors + new code/SQL rule miner
    · forge/ — Domain Forge missions, scoring, InterviewAgent
    · steward/ — the loops (ported from market_zero)
    · evals/ — eval gate, agent-lift benchmark
    · compiler/ — turns governed artifacts → compiled CTX packs

Starts as one wheel with submodules; split into separate wheels only if we ever need to. The boundary that matters is A↔B, not the seams inside B.

THE PRODUCT · neither tier · data not code

Compiled Domain Packs — versioned YAML sources + a compiled .ctx context layer + a signed manifest. The compiler (Tier B) produces them; the runtime (Tier A) consumes them. This is what gets licensed, signed, and optionally encrypted per client. commercial_analytics@1.3 is pinned by an agent the way you pin a pip dependency.

03 Context management = CTX, with governance in front

Your requirement — "every query, the right domain details are leveraged" — is exactly CTX's job, but we put a governance + relevance gate in front of the hydrator so an agent can only ever pull active, verified, in-domain knowledge. The pipeline fuses SpecOmagic's deterministic filter with CTX's LLM-as-router hydration:

  query + agent_type + pinned pack(s) + token budget
        │
        ▼   ① GOVERNANCE + RELEVANCE GATE  (runtime — deterministic)
   tag match · lifecycle gate (ACTIVE+VERIFIED only) · layer-stack resolve · budget
        │   → the set of *eligible* sections, nothing more
        ▼   ② CTX L3 DIRECTORY  (ctx — ~50 tokens, lives in system prompt)
   one line per eligible entity/section — the agent's map of what it may ask for
        │
        ▼   ③ LLM-AS-ROUTER HYDRATION  (ctx/hydrate — agent pulls only what it needs)
   ctx/hydrate(section=...) → focused prose, ~3.9k tokens/query vs 92k stuffed
        │
        ▼   ④ TRUST ENVELOPE  (runtime — aura pattern)
   assembled context + provenance + confidence + pack@version + which deltas backed it

Why this beats RAG here

CTX matches RAG fidelity (~87%) at 24× lower cost by eliminating proactive interference — the agent never sees competing/irrelevant knowledge. For governed domain packs where precision and provenance matter more than recall over a vast corpus, that's the right trade.

Governance can't be bypassed

Step ① runs in the runtime before any section is even listed in the L3 directory. A draft or deprecated artifact is invisible to the agent — not filtered after the fact, just never offered. Safety/override layers are always-included.

Same engine, three surfaces

ctx/hydrate is already an MCP tool. The REST API wraps the same call. A direct library consumer calls get_context() which runs the whole pipeline server-side. One context engine, three doors.

04 Headless — one core, three doors

Everything sits behind ontowiz-runtime. The three consumption modes are thin adapters; no business logic lives in any of them.

                         ontowiz-runtime  get_context() · query_pack() · resolve()
                                 ▲          ▲          ▲
            ① DIRECT LIBRARY          ② REST API          ③ MCP
   from ontowiz import       POST /v1/context     ctx/hydrate, pack/list,
   get_context              (ontowiz-serve)       pack/query  (ontowiz-serve)
        │                         │                    │
   trusted internal agents   networked / any       Claude & LLM-native
   (MarketZero, copilots)    language consumer      agents, IDEs, desktop

Direct-library is for your own trusted agents (lowest latency, in-process). REST is the polyglot door. MCP is the LLM-native door — and because CTX already ships an MCP server, we extend it with pack-aware tools (pack/list, pack/query, context/get) rather than build one from scratch.

05 Protecting the IP — defense in depth for client deployments

Four independent layers. Even if one is bypassed, the secret sauce holds.

① Architectural (primary)

The factory (Tier B) is never packaged into a client artifact. The client receives Tier A wheels + licensed packs only. The extraction engine, the Forge, the loops, the compiler — the things that create intelligence — physically don't ship. This is 90% of the protection and it's free, because it's just the dependency boundary.

② Packaging (for embedded runtime)

When a client must run Tier A on-prem, ship built wheels; for the most sensitive runtime logic compile to native extensions (Cython/Nuitka) so there's no readable source. The .py stays internal; the client gets a binary.

③ Pack protection (the product itself)

Compiled packs are signed (tamper-evident provenance) and optionally encrypted at rest, decrypted by the runtime with a per-client license key bound to deployment. Even the shipped YAML/.ctx isn't trivially liftable to a competitor's stack.

④ Deployment mode (strongest)

Headless makes SaaS possible: the client never receives packs or runtime — only an API/MCP endpoint we host. They consume intelligence; they hold nothing. Same core also supports on-prem container (query-only) and licensed-embed. One architecture, three commercial models.

06 Persistence — YAML for the product, Postgres for the machine

YAML / files the product

  • Pack sources — artifact YAML, git-versionable, diffable, review-as-code
  • Compiled .ctx layer — L2/L3 per pack version
  • Signed manifest — version, deps, eval scores, provenance
  • Why: knowledge-as-code. A pack diff is a reviewable PR. This is also what ships to clients.

Postgres the machine

  • Deltas + audit — governance ledger, HITL queues
  • Telemetry — which artifacts used, hit/miss, confidence (Loop 5)
  • Eval runs — agent-lift benchmarks, history
  • Forge sessions — SME rounds, consensus, scores
  • Per your call: Postgres, not SQLite. Supersedes ADR-005 (in-memory). pgvector available if we want semantic alias search later.

07 Decisions locked for this foundation (your direction, encoded)

D1 · Consolidate, don't depend

You want code in one place. We vendor/port SpecOmagic + CTX + market_zero loops into the monorepo rather than pip-depend across repos.

Monorepo with 6 packages. Original repos become upstream reference, not runtime dependencies.

D2 · Postgres for state, YAML for packs

Packs = YAML + .ctx on disk. Deltas/telemetry/evals/forge = Postgres. New ADR supersedes ADR-005.

D3 · CTX is the context engine

Vendor CTX.ai into ontowiz-ctx; governance gate runs in front of the hydrator; MCP server extended with pack tools.

D4 · Triple-door headless, library included

Direct library import for trusted agents + REST + MCP, all over one runtime. No logic in the adapters.

D5 · IP via the A/B boundary first

Architectural separation is the primary protection; signing/encryption/compilation are additive for embedded/on-prem modes.

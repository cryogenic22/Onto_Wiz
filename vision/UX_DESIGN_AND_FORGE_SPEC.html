UX design & spec for the four surfaces of the Domain Intelligence Factory — Domain Forge (gamified SME elicitation), Pack Registry (the product catalog), Knowledge Workbench (the curation back-office), and SME Impact (the motivation engine) — plus the four human-in-the-loop UX loops that drive the five backend loops. Built by growing the Situation Room, Curator and SME dashboards you already have.

The one rule that keeps the game from becoming theatre: every round, in every surface, must emit the same three things — a pack delta, a gold eval label, and a confidence update. If a screen can be played without producing all three, it is decoration and we cut it. The leaderboard is not the magic. SME judgement → structured artifact → eval case → governed pack update is the magic, and the UI's only job is to make that loop feel like sparring, not data entry.

02 Domain Forge — gamification design

The Situation Room already has the right tone: a serious reasoning exercise, not Duolingo. We protect that and scale it. The senior SME should feel like they are challenging the machine, teaching junior analysts at scale, and preserving their judgement — not running a hamster wheel for points.

Design principles

✓ Sparring room, not quiz. The frame is "can you beat / correct the machine?" The machine always proposes first; the SME reacts, challenges, refines. Reaction is easier than recall — show a senior a wrong rule and they light up.
✓ Reward useful dissent. "Everyone says X, but it fails when Y" is the best output a senior gives. Dissent that changes the pack scores higher than agreement.
✓ Close the loop visibly. The SME watches their judgement become a pack delta, then an eval, then a measurable agent improvement. That sight — not points — is the motivation engine.
✗ No points for volume. Nobody gets 500 points for clicking like a caffeinated pigeon. Speed and click-count are never scored.
✗ No blank-page interviews. The steward pre-loads weak spots; the SME never faces "tell us everything you know." Curation accelerator, not elicitation from zero.
✗ Not analyst chat. Forge is its own surface. Elicitation ≠ Q&A. We never merge it into the agent chat experience.

The three play loops

⏱️ Loop 1 — Daily 5-minute

For busy seniors. 5 steward-ranked cards. Approve / rank / correct / caveat / mark-uncertain. Keyboard-driven, fast, never more than 5. Each card = one micro-mission = one delta + eval + confidence.

🏟️ Loop 2 — Weekly Challenge

"Can you beat the machine on launch-readiness?" A messy case, the agent's proposed answer, source cards, the concept graph. The 9-step Diagnose flow + red-team. Output: richer playbook, gold answer.

👥 Loop 3 — Multiplayer Consensus

For tricky, non-binary calls. "Three SMEs disagree: payer friction or channel execution?" Output: consensus score, dissent notes, confidence weighting, an ExceptionRule capturing the situated judgement.

Scoring — "Forge Rating", not points

Replace a points counter with a calibrated judgement rating (think chess Elo for domain judgement) that only moves on things that improve the firm's brain. It is computed, never awarded for activity:

  ForgeRating moves on five signals — none of them volume or speed:

  correctness   agreement with eventual consensus / gold outcome
  novelty       created a *new* artifact vs confirmed an existing one
  impact        blast-radius × downstream agent usage of the artifact
  eval value    produced a gold EvalCase that catches a real error
  dissent value productive disagreement that *changed* the pack   ← weighted highest

  decay: contributions that go stale or unused lose weight over time
  anti-gaming: consensus-weighted; identical rapid clicks are ignored, not rewarded

The SME Impact dashboard renders this as a story, not a scoreboard: "Your judgement shapes 3 active packs, prevented 11 agent errors this quarter, and your dissent on pull-through overrode the base definition for 4 client teams." Dissent gets its own badge — being usefully, provably contrarian is the highest status.

04 Knowledge Workbench — the curation back-office

Grow the Curator dashboard from "review deltas" into the serious back office the spec describes. This is where the machine's rough baseline gets cleaned before the game, so the Forge is a curation accelerator, not a blank page.

Candidate Inbox NEW

Loop 1 mining output: extracted candidates as PROPOSED deltas, grouped by concept, with confidence + source provenance. Bulk triage; send weak/high-impact ones to the Forge as missions.

Duplicate Clusters NEW

"These 5 candidates are the same concept seen in 3 decks." Merge into one canonical artifact, preserving provenance from all sources.

Conflict Board NEW

Where artifacts, sources, or SMEs disagree (CTX flags conflicts at compile). Resolve to consensus or capture an ExceptionRule. Conflict density is a tracked metric.

Concept Graph NEW

The ontowiz-core NetworkX graph, visualized: concepts, relationships, supports / contradicts edges. Click a node to inspect its artifacts and evidence.

Coverage Heatmap NEW

Domain × artifact-kind grid: green = codified + eval-covered, amber = codified no evals, red = gap. The map that tells the steward where to send the Forge next.

Delta Review + Audit REUSE

Your existing ReviewQueue / DeltaDetail / AuditTrail, unchanged — the governance core every other panel feeds into.

05 The UX loops — the human side of the five backend loops

"Design loops for it" — here they are. Each surface is the human touchpoint of a backend loop. The discipline: every loop has a trigger (what surfaces the work), an act (what the human does), and a visible result (the human watches their judgement land). The visible result is what makes seniors come back.

Loop A — Daily Forge loop · human side of backend Loop 2 (steward) + Loop 3 (elicitation)

steward ranks weak spots → 5 daily cards → SME plays → delta + eval + confidence → pack quality moves → tomorrow's cards are different Surfaces: Domain Forge (daily) → SME Impact. Visible result: "your call on the IQVIA lag is now live in market_access@0.5 and blocks a known bad answer."

Loop B — Curation loop · human side of backend Loop 1 (mining)

mining proposes candidates → Workbench Candidate Inbox → curator triages / merges / resolves conflicts → governed deltas → compiler ships a pack version Surfaces: Knowledge Workbench → Pack Registry. Visible result: coverage heatmap turns a red cell green; a new pack version appears in the registry.

Loop C — Pack lifecycle loop · human side of backend Loop 4 (eval gate)

pack compiles → eval gate runs → Registry shows lift / coverage / gaps → gaps auto-generate Forge missions → SMEs close them → next version Surfaces: Pack Registry ⇄ Domain Forge. Visible result: agent-lift bar goes up between versions; "9 gaps" becomes "3 gaps."

Loop D — Consumption-correction loop · human side of backend Loop 5 (feedback)

agents use packs → telemetry + corrections → surfaced as "this pack caused an error" cards → SME confirms → delta + new EvalCase → pack improves Surfaces: agent runtime → Domain Forge / Workbench. Visible result: one correction becomes an eval that prevents the whole class of error — the "correction reuse" metric, made visible.

What the UI needs from the API/MCP (shapes F3 serve)

  • GET /v1/packs, /v1/packs/{id} (manifest, overlays, evals, diff) — Registry
  • GET /v1/packs/{id}/explain?concept= — lineage
  • GET /v1/missions/daily (steward-ranked), POST /v1/missions/{id}/submit → delta+eval+confidence — Forge
  • GET /v1/candidates, /v1/conflicts, /v1/coverage, /v1/graph — Workbench
  • GET /v1/impact/{sme} — Impact story; existing Delta/audit routes — reuse
